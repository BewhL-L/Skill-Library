# 项目治理

## 📋 概述

本文档描述 Obsidian 知识库标准化生成器的项目治理结构、决策流程、角色职责和社区规范。

---

## 🏛️ 治理原则

### 1. 开放透明
- 所有决策过程公开透明
- 讨论和决策记录可追溯
- 项目路线图和优先级公开

### 2. 精英治理
- 基于贡献和能力获得影响力
- 代码质量和社区贡献是晋升依据
- 所有贡献者平等对待

### 3. 社区驱动
- 功能优先级基于社区需求
- 鼓励用户参与设计和决策
- 维护者服务于社区，而非控制社区

### 4. 技术卓越
- 代码质量是首要标准
- 测试覆盖率不降低
- 持续改进架构和性能

## 👥 角色与职责

### 项目创建者（BDFL）

**职责**：
- 项目最终决策人
- 项目愿景和方向把控
- 重大变更的最终审批
- 社区冲突的最终仲裁

**当前担任**：项目创建者

**任期**：终身（可主动移交）

### 核心维护者（Core Maintainers）

**职责**：
- 日常项目维护
- Pull Request 审核和合并
- Issue 分类和处理
- 版本发布管理
- 社区管理和支持

**权限**：
- 合并 Pull Request
- 创建和删除分支
- 管理 Issue 和 PR 标签
- 发布新版本
- 管理 GitHub 仓库设置

**晋升标准**：
- 持续贡献 3 个月以上
- 合并 10+ 个有意义的 PR
- 审核 20+ 个 PR
- 熟悉项目架构和代码规范
- 获得现有核心维护者的一致推荐

### 贡献者（Contributors）

**职责**：
- 贡献代码、文档、翻译
- 报告 Bug 和建议功能
- 参与社区讨论
- 帮助新用户

**权限**：
- 创建 Issue 和 PR
- 参与讨论
- 审核其他贡献者的 PR（非强制）

**如何成为贡献者**：
- 提交第一个被合并的 PR
- 或报告 3+ 个有效 Bug
- 或贡献有价值的文档/翻译

### 社区成员（Community Members）

**职责**：
- 使用项目并提供反馈
- 参与社区讨论
- 帮助其他用户
- 推广项目

**如何成为社区成员**：
- 使用项目
- 加入社区讨论
- 遵守行为准则

## 📝 决策流程

### 日常决策

**适用范围**：
- Bug 修复
- 文档改进
- 小功能添加
- 依赖更新

**流程**：
1. 贡献者提交 PR
2. 至少 1 名核心维护者审核
3. 审核通过后合并
4. 无需正式投票

### 重要决策

**适用范围**：
- 新功能设计
- 架构变更
- API 变更
- 重大重构

**流程**：
1. 提交 RFC（Request for Comments）文档
2. 社区讨论至少 7 天
3. 收集反馈并修订
4. 核心维护者投票（简单多数通过）
5. 实施并记录决策

### 重大决策

**适用范围**：
- 项目方向变更
- 许可证变更
- 治理结构变更
- 项目移交或归档

**流程**：
1. 项目创建者发起提案
2. 社区讨论至少 30 天
3. 核心维护者一致同意
4. 项目创建者最终批准
5. 正式公告并记录

## 🔄 Pull Request 流程

### 提交前检查

- [ ] 代码遵循项目规范
- [ ] 所有测试通过
- [ ] 添加了必要的测试
- [ ] 更新了相关文档
- [ ] 提交信息遵循 Conventional Commits
- [ ] PR 描述清晰完整

### 审核流程

1. **自动检查**：CI/CD 运行测试、lint、类型检查
2. **初步审核**：核心维护者检查代码质量和设计
3. **详细审核**：至少 1 名核心维护者详细审核
4. **修改迭代**：根据审核意见修改
5. **最终批准**：审核者批准
6. **合并**：核心维护者合并到主分支

### 审核标准

- **代码质量**：可读性、可维护性、性能
- **测试覆盖**：新功能有测试，不降低整体覆盖率
- **文档完整**：API 文档、使用示例、变更记录
- **向后兼容**：不破坏现有功能，或提供迁移指南
- **安全**：不引入安全漏洞

## 🚀 版本发布

### 版本号规范

遵循 [语义化版本](https://semver.org/lang/zh-CN/)：

- **主版本号（Major）**：不兼容的 API 变更
- **次版本号（Minor）**：向下兼容的功能性新增
- **修订号（Patch）**：向下兼容的问题修正

### 发布流程

详细发布流程请参考 [RELEASE.md](RELEASE.md)。

### 发布频率

- **Patch 版本**：随时发布（Bug 修复）
- **Minor 版本**：每月 1 次（新功能）
- **Major 版本**：每年 1-2 次（重大变更）

## 🤝 社区规范

### 行为准则

所有社区成员必须遵守 [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md)。

### 沟通渠道

| 渠道 | 用途 | 响应时间 |
|------|------|---------|
| GitHub Issues | Bug 报告、功能请求 | 3-5 个工作日 |
| GitHub Discussions | 一般讨论、问答 | 1-3 个工作日 |
| GitHub PR | 代码贡献 | 3-7 个工作日 |
| 邮件 | 安全问题、私人事务 | 5-7 个工作日 |

### 标签体系

#### Issue 标签

| 标签 | 用途 |
|------|------|
| `bug` | Bug 报告 |
| `enhancement` | 功能请求 |
| `documentation` | 文档相关 |
| `good first issue` | 适合新手的任务 |
| `help wanted` | 需要帮助 |
| `question` | 问题咨询 |
| `duplicate` | 重复 Issue |
| `wontfix` | 不会修复 |
| `invalid` | 无效 Issue |
| `security` | 安全相关 |

#### PR 标签

| 标签 | 用途 |
|------|------|
| `work in progress` | 开发中，暂不审核 |
| `needs review` | 需要审核 |
| `needs changes` | 需要修改 |
| `approved` | 已批准 |
| `breaking change` | 破坏性变更 |
| `dependencies` | 依赖更新 |

## 🛡️ 安全治理

### 安全报告

安全漏洞必须私下报告，参考 [SECURITY.md](SECURITY.md)。

### 安全响应

- 24 小时内确认收到报告
- 3 个工作日内评估严重程度
- 7 个工作日内制定修复计划
- 关键漏洞 7 天内发布修复

### 安全审计

- 每次发布前运行安全扫描
- 每季度进行一次完整安全审计
- 依赖更新及时跟进安全补丁

## 📊 项目健康指标

### 代码质量

- 测试覆盖率 ≥ 90%
- 代码质量 0 错误 0 警告
- 类型注解覆盖率 100%
- CI/CD 全部通过

### 社区健康

- Issue 响应时间 ≤ 5 个工作日
- PR 审核时间 ≤ 7 个工作日
- 活跃贡献者 ≥ 3 人
- 社区讨论活跃度

### 发布健康

- 定期发布（每月至少 1 次）
- 变更日志完整
- 向后兼容性良好
- Bug 修复及时
