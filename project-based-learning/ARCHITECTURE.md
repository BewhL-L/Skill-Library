# ARCHITECTURE

本 Skill 是**纯文档型**：没有脚本、没有可执行代码，质量完全取决于"约束写得够不够硬"和"模板够不够细"。

## 1. 组成

```
project-based-learning/
├── SKILL.md                          主流程：原则 / 8 部分概览 / 工作流 / 输出规范 / 质量清单
├── references/
│   ├── project-templates.md          8 大部分的逐段模板（生成时按部分取用）
│   └── project-types-and-templates.md  8 类项目的需求模板与知识点覆盖矩阵
├── examples/                         方案节选与好坏对照（让人知道"合格长什么样"）
├── QUICKSTART / API / TESTING / DEBUGGING / FAQ / INSTALLATION / SECURITY / CONTRIBUTING
└── README / CHANGELOG / LICENSE
```

分层逻辑：

| 层 | 载体 | 作用 | 修改频率 |
|---|---|---|---|
| 规则层 | `SKILL.md` | 什么必须做、什么禁止做 | 低（改一次影响所有产出） |
| 模板层 | `references/*.md` | 每部分/每类型的具体结构与要点 | 中（新增项目类型时改） |
| 示例层 | `examples/` | 合格与不合格的对照样本 | 中 |
| 说明层 | 其余根目录文档 | 给使用者和维护者看的 | 高（不影响产出） |

## 2. 决策流

```mermaid
graph TD
    A[用户提出项目需求] --> B{主题是否具体?}
    B -->|否| C[追问类型/技术栈/周期]
    C --> B
    B -->|是| D{已有项目?}
    D -->|是| E[扩展方案分支: 影响分析 + 改动清单]
    D -->|否| F[定类型 → 取 references 类型模板]
    F --> G[按 8 部分模板逐段生成]
    G --> H[每阶段补 [[]] 双链]
    H --> I[验收改写为 命令 + 期望输出]
    I --> J{质量清单全过?}
    J -->|否| K[定位缺失部分并补齐]
    K --> J
    J -->|是| L[交付 8 大部分]
```

## 3. 为什么没有脚本

三个候选理由，逐条排除后仍成立：

1. **产出是自然语言**——8 大部分是论证与设计，不是结构化数据，脚本只能校验形状，不能替代判断；
2. **约束靠"硬性要求 + 清单"落地**——`SKILL.md` 的输出规范与质量清单已经能拦住占位符、空验收；
3. **一旦上脚本，会诱导把"通过脚本"当成"方案合格"**——真正的失败模式是"验收不可执行""选型没理由"，这些机器判不了。

代价也要说清：**没有自动化回归**，改模板后只能靠人抽查（方法见 `TESTING.md`）。

## 4. 扩展点

| 需求 | 改哪里 | 同步项 |
|---|---|---|
| 新增项目类型（如"数据工程管道"） | `references/project-types-and-templates.md` 加一节 | `SKILL.md`「常见项目类型参考」表加一行 |
| 调整 8 大部分结构 | `references/project-templates.md` 对应部分 | `SKILL.md`「8 大部分概览」表 + `API.md` 输出契约 |
| 加严验收要求 | `SKILL.md`「工程实践基线」+ 质量清单 | `TESTING.md` 的抽查命令 |
| 调整下游交接 | `SKILL.md`「与其他 Skill 的协作」 | `API.md` 第 5 节 |

**规则**：模板与主表是"一处改、三处同步"的关系，只改一处必然产生自相矛盾（这是本 Skill 最容易腐化的地方）。

## 5. 与三件套的关系

本 Skill 处在最上游：它决定"做什么、为什么这么选"，下游负责"跑起来"和"怎么学"。

```
方案（本 Skill） → 项目（project-scaffolder） → 指南（project-processization）
```

越靠上游，错误的代价越大：方案里选型错了，下游两周的代码都白写。所以本 Skill 的验收重点不是"写得多"，而是"**决策有没有理由、验收能不能执行**"。
