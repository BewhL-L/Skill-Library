# bug-troubleshooter 常见问题解答

> 使用 Bug 排查助手时的常见问题和解答。

---

## Q1：我只提供了错误信息，能排查出根因吗？

**A**：错误信息是排查的起点，但完整的排查需要更多上下文：
1. **错误信息**：完整的错误堆栈（包括 Caused by 链）
2. **发生环境**：操作系统、JDK/Node/Python 版本、框架版本
3. **发生场景**：在什么操作下出现的？是必现还是偶发？
4. **近期变更**：最近改了什么代码/配置/依赖？
5. **已尝试**：已经试过什么排查方法？结果如何？

提供的信息越完整，排查越精准。如果信息不足，Skill 会先列出需要补充的信息，或者给出最可能的几个原因和验证方法。

---

## Q2：排查报告中的"可能原因"有好几个，我怎么知道哪个是对的？

**A**：排查报告中的可能原因按**可能性排序**，每个原因都有**验证方法**。按顺序验证：
1. 从第一个（可能性最高）开始，按验证方法检查
2. 如果验证结果符合该原因的特征，基本可以确定根因
3. 如果不符合，继续验证下一个原因
4. 如果所有原因都不符合，补充更多信息后重新排查

排查是一个**假设→验证**的迭代过程，不是一次性给出答案。关键是每个假设都有可执行的验证方法，而不是瞎猜。

---

## Q3：偶发问题怎么排查？复现不了怎么办？

**A**：偶发问题的排查策略：
1. **加强日志**：在关键路径添加详细日志，记录上下文信息（请求参数、用户ID、时间戳、系统状态）
2. **监控埋点**：添加指标监控，捕捉异常时的系统状态（CPU、内存、连接数、GC）
3. **链路追踪**：用 SkyWalking/Zipkin 追踪完整调用链，找到异常节点
4. **灰度对比**：对比正常和异常时的差异（配置、数据、流量）
5. **压力复现**：测试环境加压，尝试稳定复现
6. **常见偶发原因**：并发问题（竞态条件、死锁）、资源耗尽（连接池、线程池）、网络抖动、缓存击穿、数据脏读

偶发问题排查需要耐心，关键是**收集足够的上下文信息**，在问题发生时能还原现场。

## Q4：性能问题怎么排查？接口响应慢但没有报错

**A**：性能问题的排查路线：
1. **定位瓶颈**：先确定是 CPU 密集、IO 密集、还是内存问题
   - 看服务器监控（CPU、内存、IO、网络）
   - 看应用监控（接口响应时间、QPS、错误率）
2. **应用层排查**：
   - 慢接口：用 Arthas（Java）/ clinic（Node）/ py-spy（Python）trace 方法调用耗时
   - 慢 SQL：开启慢查询日志，用 EXPLAIN 分析执行计划
   - 频繁 GC：看 GC 日志，分析内存使用
   - 线程阻塞：jstack 看线程状态，是否有锁等待
3. **数据库层**：
   - 慢查询、锁等待、连接池满、索引失效
4. **缓存层**：
   - 命中率低、穿透/击穿/雪崩、大 key/热 key
5. **优化验证**：
   - 优化后对比性能指标（响应时间、QPS、资源使用率）
   - 用压力测试验证优化效果

关键是**用数据说话**，不要凭感觉优化。先定位瓶颈，再针对性优化。

## Q5：排查后给的修复方案，我改了但问题还在怎么办？

**A**：这种情况说明根因定位不准确，需要重新排查：
1. **确认修复是否生效**：
   - 代码是否正确部署？（清缓存、重启、确认版本）
   - 配置是否正确加载？（看启动日志、确认配置源）
   - 修复是否覆盖了所有场景？（可能只修了一部分）
2. **重新收集信息**：
   - 修复后的错误信息是否有变化？
   - 是否有新的错误线索？
   - 问题发生的频率/场景是否有变化？
3. **换排查方向**：
   - 之前的假设是否有遗漏？
   - 是否有其他可能原因被忽略？
   - 是否需要更深入的排查（如源码级分析）？
4. **求助外部资源**：
   - 搜索错误信息（Stack Overflow、GitHub Issues、官方文档）
   - 咨询有经验的同事/社区

排查是迭代过程，一次定位不准很正常。关键是每次排查都收集新信息，逐步缩小范围。

## Q6：可以生成排查 Checklist 吗？我想自己一步步查

**A**：可以。Skill 支持生成系统化的排查 Checklist，如：
- "Spring Boot 启动失败排查 Checklist"（10+ 项，按顺序排列）
- "前端白屏排查 Checklist"
- "MySQL 慢查询排查 Checklist"
- "Redis 连接失败排查 Checklist"

每个 Checklist 项包含：
- 检查什么（具体检查点）
- 怎么查（命令/工具/方法）
- 正常结果（预期值）
- 异常说明（如果不正常，可能是什么原因）

Checklist 适合偶发问题或需要系统性排查的场景，可以避免遗漏检查点。

## Q7：排查完的问题怎么沉淀，避免以后再踩坑？

**A**：排查后建议做以下沉淀：
1. **更新知识库笔记**：
   - 在对应技术概念的笔记中添加「问题」模块
   - 记录问题现象、原因、解决方案、预防措施
   - 用 `note-quality-evaluator` 检查笔记质量
2. **纳入复习计划**：
   - 用 `knowledge-review-spaced` 把排查总结纳入复习
   - 间隔重复巩固，避免重复踩坑
3. **整理速查表**：
   - 用 `cheatsheet-generator` 把常见问题整理成速查表
   - 遇到类似问题可以快速查阅
4. **代码层面预防**：
   - 添加监控告警（问题发生时及时发现）
   - 添加单元测试（覆盖异常场景）
   - 添加日志（问题发生时有足够上下文）
   - 代码注释（标注容易踩坑的地方）

排查的价值不仅在于解决当前问题，更在于沉淀经验，避免以后重复踩坑。
