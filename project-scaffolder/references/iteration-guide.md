# 增量更新与多轮迭代指南

> 本文件定义项目生成后的迭代修改流程。首次生成后，用户几乎一定会要求修改、扩展或优化。本指南确保每次迭代都能高质量完成，不引入回归问题。

---

## 核心理念

1. **先探查再修改**：禁止凭记忆修改，必须先读取实际文件确认当前状态
2. **最小变更原则**：只改用户点名的范围，不主动扩展任务
3. **同步更新原则**：代码变更必须同步更新文档和测试
4. **验证后交付**：每次修改后必须验证，不把"看起来没问题"当交付
5. **可追溯**：每次修改都有 Git 提交，记录变更内容和原因

---

## 迭代触发场景分类

| 场景类型 | 典型用户说法 | 处理策略 |
|---------|------------|---------|
| Bug 修复 | "这里报错了""跑不通""有问题" | 复现→定位根因→修复→验证 |
| 功能新增 | "加一个 XX 功能""能不能支持 XX" | 需求分析→规划→实现→同步文档→验证 |
| 内容优化 | "这个页面不好看""体验不好""优化一下" | 问题分析→方案设计→实现→验证 |
| 需求变更 | "我想改成 XX""不要这个了" | 影响评估→修改→清理旧代码→同步文档 |
| 阶段推进 | "继续下一批""进入下一阶段" | 确认上一阶段完成→启动下一阶段 |
| 深度扩展 | "加 WebSocket""加推荐算法""加缓存" | 技术选型→架构设计→实现→测试→文档 |

---

## 标准迭代流程（五步）

### 第一步：现状探查（必须先做）

**禁止**：凭记忆、凭摘要、凭"应该是这样"直接修改。

**必须做**：
1. **读取文件**：读取用户点名的文件，确认当前实际内容
2. **复现问题**：如果是 Bug，运行项目复现用户描述的问题，记录错误信息
3. **确认范围**：明确修改涉及哪些文件，列出修改清单
4. **检查依赖**：修改的文件被哪些其他文件引用，修改是否会影响它们

**探查输出**：
- 当前文件内容摘要
- 问题复现结果（如适用）
- 修改文件清单
- 潜在影响范围

### 第二步：影响评估

修改前评估以下内容：

| 评估项 | 具体内容 |
|--------|---------|
| 直接影响 | 修改的文件本身 |
| 联动影响 | 引用该文件/模块的其他文件 |
| 文档影响 | README/指导文档是否需要同步更新 |
| 测试影响 | 是否需要新增/修改测试 |
| 数据影响 | 是否需要数据库迁移/旧数据处理 |
| 风险等级 | 低（单文件）/中（多文件联动）/高（架构变更） |

**影响评估输出**：
- 完整的修改文件清单（含文档和测试）
- 风险等级
- 是否需要用户确认（高风险时）

### 第三步：执行修改

**修改原则**：
1. **只改被点名的范围**：用户说"改 A"就只改 A，不顺便改 B/C/D
2. **保留未要求改动的内容**：不重构、不优化、不"顺便"改其他地方
3. **遵守生成质量约束**：新增功能必须遵守 SKILL.md 第三步的 8 条约束
4. **保持代码风格一致**：与项目现有风格保持一致，不引入新的编码风格
5. **注释说明**：非显而易见的修改加注释说明原因

**修改顺序**（多文件时）：
1. 先改底层（模型/服务/工具函数）
2. 再改上层（路由/页面/组件）
3. 最后改文档和测试

### 第四步：同步更新

**代码变更必须同步更新以下内容**：

| 变更类型 | 必须同步更新 |
|---------|------------|
| 新增/修改 API | 前端 API 封装 + README 功能列表 + 指导文档操作指引 |
| 新增数据模型 | 数据库迁移说明 + README 模型数 + 指导文档 |
| 新增页面 | app.json 注册 + README 页面数 + 指导文档 |
| 修改功能逻辑 | 指导文档操作指引 + 测试用例 |
| 新增依赖 | requirements.txt/package.json + README 技术栈 |
| 修复 Bug | 指导文档风险排查（如适用） |

**禁止**：
- ❌ 只改代码不改文档
- ❌ 只改后端不改前端
- ❌ 只改功能不改测试
- ❌ README 写 9 个页面但实际有 12 个

**Skill 自身修改的特殊要求**（修改 project-scaffolder 本身时）：

每次修改 SKILL.md 或 references/ 时，**必须同步更新 CHANGELOG.md**：

| 修改类型 | CHANGELOG 操作 |
|---------|---------------|
| 新增功能/维度/约束 | 在最新版本的 `✨ 新功能` 下添加条目 |
| 修复 Bug | 在最新版本的 `🐛 Bug 修复` 下添加条目 |
| 新增 references 文件 | 在最新版本的 `📝 文档` 下添加条目 |
| 重构/性能优化 | 在最新版本的 `🏗️ 工程化` 下添加条目 |
| 版本号升级 | 新增版本标题，含日期和版本号 |

**规则**：
- CHANGELOG 必须在同一次修改中更新，不允许"改完 SKILL 再补 CHANGELOG"
- 每次修改至少在 CHANGELOG 中添加 1 条记录
- 版本号按语义化版本规则升级（功能新增→次版本号，Bug修复→修订号，架构变更→主版本号）
- **禁止**：修改了 SKILL.md 但 CHANGELOG 还是旧内容

### 第五步：验证与交付

**验证清单**（每次迭代至少完成以下 3 项）：

1. **功能验证**：
   - 修改的功能是否正常工作
   - 相关功能是否受影响（回归测试）
   - 边界情况是否处理

2. **技术验证**（代码类项目）：
   - 后端：`python -c "from app.main import app"` 无导入错误
   - 前端：编译无错误
   - 测试：相关测试全部通过
   - 数据库：模型能被 ORM 识别，表结构正确

3. **文档验证**：
   - README 与实际代码一致（功能列表/页面数/模型数）
   - 指导文档与实际产物一致（分工/操作指引）
   - 文档链接无死链

**交付内容**：
1. Git 提交（遵循 Conventional Commits：`fix:`/`feat:`/`refactor:`/`docs:`）
2. 向用户说明：
   - 改了什么（具体文件和功能）
   - 为什么这么改（选型理由/问题根因）
   - 如何验证（运行什么命令/操作什么步骤）
   - 还有什么需要用户做

## 常见迭代场景处理

### 场景 1：Bug 修复

**流程**：
1. 复现 Bug，记录完整错误信息
2. 定位根因（不是修表象，是修根因）
3. 修复
4. 验证修复有效 + 无回归
5. 提交

**常见坑**：
- ❌ 只修报错的地方，不修根因（如只加 try/except 吞掉错误）
- ❌ 修复后不验证，直接交付
- ❌ 修复一个 Bug 引入三个新 Bug

**示例**：
> 用户："发布帖子报错 500"
> 探查：运行后端，复现错误，发现是 image_urls 字段为空时 split 报错
> 根因：create_post 没有处理空图片列表
> 修复：加 if not image_urls: raise HTTPException(400, "至少上传一张图片")
> 验证：空图片返回 400，正常图片发布成功
> 提交：fix: 修复发布帖子空图片列表导致500错误

### 场景 2：功能新增

**流程**：
1. 需求分析（这个功能解决什么问题、核心流程是什么）
2. 功能完整性检查（对照 content-completeness.md，是否有联动功能需要同步加）
3. 后端实现（模型→服务→路由→测试）
4. 前端实现（API 封装→页面→交互）
5. 文档同步（README + 指导文档）
6. 验证 + 提交

**常见坑**：
- ❌ 只加后端不加前端（功能完整性反向检查会发现）
- ❌ 只加功能不加测试
- ❌ 加了功能不更新文档

### 场景 3：多轮批量推进

**用户偏好**：用户设定了默认指令——要求继续执行任务时 AI 可以自动继续下一批，无需再次征求同意。

**流程**：
1. 确认当前批次范围
2. 完成当前批次
3. 验证当前批次
4. 自动启动下一批（无需询问）
5. 全部完成后统一交付

**注意**：
- 每批完成后必须验证，不积累问题
- 遇到阻塞性问题立即停止并告知用户
- 全部完成后做一次全面自检

## 回滚策略

如果修改后发现问题严重，需要回滚：

1. **Git 回滚**：`git revert <commit_id>` 或 `git reset --hard <commit_id>`
2. **数据库回滚**：如果涉及数据库变更，需要恢复旧表结构/旧数据
3. **文档回滚**：同步回滚文档变更
4. **重新分析**：回滚后重新分析问题，不要盲目重试同样的修改

**预防措施**：
- 每次修改前确认 Git 有干净的提交点
- 高风险修改先在分支上做，验证后再合并
- 数据库修改前备份旧数据库

---

## 迭代质量检查清单

每次迭代完成后，对照以下清单检查：

- [ ] 修改前读取了实际文件，不是凭记忆修改
- [ ] 只改了用户点名的范围，没有主动扩展
- [ ] 新增功能遵守了 8 条生成质量约束
- [ ] 代码变更同步更新了 README
- [ ] 代码变更同步更新了指导文档
- [ ] **修改 Skill 自身时同步更新了 CHANGELOG.md**（含版本号升级）
- [ ] 新增/修改功能有对应的测试
- [ ] 运行了相关测试，全部通过
- [ ] 后端无导入错误，前端无编译错误
- [ ] Git 提交信息遵循 Conventional Commits
- [ ] 向用户说明了改了什么、为什么、如何验证

---

*迭代是项目生命周期的常态，不是例外。每次迭代都按本流程执行，确保质量稳定，不积累技术债。*
