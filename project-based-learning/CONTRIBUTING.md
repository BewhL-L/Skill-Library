# CONTRIBUTING

个人维护的技能，不开放外部贡献。以下约定用于未来的自己。

## 1. 改动前

1. 先跑一次 `TESTING.md` 第 1 节的五条抽查，记下当前基线；
2. 明确改动类型：**规则**（SKILL.md）/ **模板**（references/）/ **说明**（其余文档）；
3. 规则与模板的改动会影响所有产出，说明类文档只影响阅读。

## 2. 一处改、三处同步

本 Skill 最容易腐化的地方是"表与模板各说各话"。改动必须成组：

| 改动 | 必须同步 |
|---|---|
| 8 大部分结构调整 | `SKILL.md`「8 大部分概览」表 + `references/project-templates.md` + `API.md` 输出契约 |
| 新增项目类型 | `references/project-types-and-templates.md` + `SKILL.md`「常见项目类型参考」表 |
| 验收要求加严 | `SKILL.md`「工程实践基线」+ 质量清单 + `TESTING.md` 抽查命令 |
| 下游交接方式变化 | `SKILL.md`「与其他 Skill 的协作」+ `API.md` 第 5 节 |

## 3. 写作约定

- 每部分模板给**结构 + 要点**，不给整段范文——范文会被逐字复制，结构才能约束质量；
- 反面例子与正面例子成对出现（"差 / 好"两列），只讲原则等于没讲；
- 禁止出现 `XXX`、`待补充`、`...` 这类占位符（`TESTING.md` 第① ②条会抓）；
- 中文标点，代码块内用 ASCII 引号。

## 4. 版本与记录

| 变更 | 版本位 |
|---|---|
| 新增/调整规则、8 部分结构 | MINOR（1.0.x → 1.1.0） |
| 模板细节、示例、文档 | PATCH（1.0.2 → 1.0.3） |
| 破坏下游交接契约 | MAJOR，并在 CHANGELOG 写明迁移方式 |

`CHANGELOG.md` 用 Keep a Changelog 格式，条目写"改了什么 + 为什么"，不写"优化若干"。

## 5. 交付前自查

- [ ] `TESTING.md` 五条抽查对最新一次生成仍成立
- [ ] `SKILL.md` 页脚版本号 = `CHANGELOG.md` 最新条目
- [ ] 表与模板无矛盾（8 部分名称、顺序、必填字段一致）
- [ ] 新增文档已加入 `README.md` 的文档结构树
