## 🚨 报告安全漏洞

如果你发现了安全漏洞，请**不要**在公开的 Issue 中报告，而是通过以下方式私下报告：

### 报告方式

1. **GitHub Security Advisories**（推荐）
   - 前往项目仓库的 Security 选项卡
   - 点击 "Report a vulnerability"
   - 填写漏洞详情

2. **邮件报告**
   - 发送邮件至：security@example.com
   - 邮件标题格式：`[Security] <漏洞简述>`

### 报告内容

请在报告中包含以下信息：

1. **漏洞描述**：清晰描述漏洞是什么
2. **影响范围**：受影响的版本和功能
3. **复现步骤**：详细的复现步骤
4. **预期行为**：正常情况下应该是什么样
5. **实际行为**：实际发生了什么
6. **攻击场景**：可能的利用方式
7. **修复建议**：如果你有修复思路
8. **附加信息**：截图、日志、PoC 代码等

## ⏱️ 响应时间

我们将按照以下时间线响应安全报告：

| 阶段 | 时间 | 说明 |
|------|------|------|
| 初步确认 | 24 小时内 | 确认收到报告，开始评估 |
| 漏洞评估 | 3 个工作日内 | 评估漏洞严重程度和影响范围 |
| 修复计划 | 7 个工作日内 | 制定修复计划和时间表 |
| 修复发布 | 根据严重程度 | 关键漏洞 7 天内，一般漏洞 30 天内 |
| 公开披露 | 修复发布后 | 在修复发布后适当时间公开披露 |

## 🎯 漏洞严重程度分级

我们使用以下标准评估漏洞严重程度：

### 🔴 严重（Critical）
- 远程代码执行（RCE）
- 任意文件读写
- 权限提升到管理员
- 敏感数据大规模泄露
- 影响所有用户的漏洞

### 🟠 高（High）
- 权限提升
- 敏感信息泄露
- 拒绝服务（DoS）
- 跨站脚本（XSS）
- SQL 注入

### 🟡 中（Medium）
- 信息泄露（非敏感）
- 有限的拒绝服务
- 不安全的默认配置
- 缺少安全头

### 🟢 低（Low）
- 信息泄露（公开信息）
- 最佳实践建议
- 轻微的安全问题

## 🛡️ 安全最佳实践

### 用户安全建议

1. **保持更新**：始终使用最新版本
2. **审查代码**：在生产环境使用前审查代码
3. **限制权限**：不要以管理员权限运行
4. **备份数据**：定期备份知识库数据
5. **使用 HTTPS**：如果通过网络访问，使用 HTTPS

### 开发者安全实践

1. **依赖审计**：定期运行 `safety check` 检查依赖漏洞
2. **代码扫描**：使用 `bandit` 进行 Python 安全扫描
3. **密钥管理**：不要在代码中硬编码密钥
4. **输入验证**：所有用户输入都要验证和清理
5. **安全测试**：CI/CD 中集成安全扫描
