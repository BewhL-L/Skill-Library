# QUICKSTART

三分钟拿到一份能落地的项目方案。本 Skill **只出方案**，不生成项目代码。

## 一句话用法

给它四件事：**做什么、练哪些技术、多久、要不要联动知识库**。它回你 8 大部分。

## 最短输入

```
我想做一个 RAG 知识库问答系统练手，
技术栈 Python + FastAPI + LangChain + Chroma，周期 4 周，
要能写进简历，并和我的 Obsidian 知识库联动。
```

缺项也能跑，但会按默认补：类型→AI RAG 应用、难度→⭐⭐⭐、周期→4 周。**技术栈不写，选型会变成通用建议**，这是最常见的质量损失点。

## 你会拿到什么

| # | 部分 | 你应该能一眼判断 |
|---|---|---|
| 一 | 项目概述 | 类型/难度/周期/最终产物是否对得上你的目标 |
| 二 | 需求文档 | 功能是否有优先级（P0/P1），非功能是否有数字 |
| 三 | 技术选型 | 每层是否有"为什么选 A 不选 B" |
| 四 | 架构设计 | 架构图 + 目录结构 + 表结构 + API 是否齐 |
| 五 | 分步实现教程 | 每阶段是否有可运行产物、是否标注 `[[笔记]]` |
| 六 | 验收标准 | 每条是否能复制成命令并给出期望输出 |
| 七 | 扩展方向 | 是否具体到"加什么、解决什么问题" |
| 八 | 学习资源 | 是否指向官方文档而非二手转述 |

## 拿到方案后的三步

1. **自查**：用 `TESTING.md` 的 5 条命令过一遍（结构、占位符、双链、验收可执行性）。
2. **落地**：要生成可运行项目 → 交给 `project-scaffolder`；方案里的选型与架构直接作为输入，不要重规划。
3. **验收**：项目做完 → 交给 `project-processization` 做事实核查与精读指南。

## 三种常见用法

| 场景 | 说法 | 产出 |
|---|---|---|
| 要整套方案 | "帮我规划一个 XX 项目" | 8 大部分完整方案 |
| 只要一部分 | "只生成架构设计" / "补一下验收标准" | 该部分详细内容 + 与整体的衔接说明 |
| 在现有项目上加 | "我这个项目想加 RAG，出个扩展方案" | 影响分析 + 改动清单 + 新验收点 |

## 三个别指望它做的事

- 不生成项目代码（→ `project-scaffolder`）
- 不写逐章精读指南（→ `project-processization`）
- 不替你判断该不该做这个项目（选型服从你的学习路线，见 `learning-path-planner`）
