# DEBUGGING

"方案不好用"通常不是模型不会写，而是**某一条约束没落到纸面**。下面按症状给诊断路径。

## 1. 症状 → 原因 → 处理

| 症状 | 最可能的原因 | 处理 |
|---|---|---|
| 8 部分都在，但读起来像模板 | 没有把用户的**技术栈与学习目标**写进约束，模型只能套模板 | 重生成时显式给技术栈 + 想练的点，并要求"每部分引用至少一个用户给的技术名词" |
| 验收标准全是"运行正常""性能良好" | 验收没按"命令 + 期望输出"写 | 逐条改写，见 `SKILL.md`「工程实践基线」第 1 条；一条写不出命令的验收 = 该阶段目标不清 |
| 周期估算明显失真（4 周做微服务） | 难度与周期没有联动校验 | 要么拆里程碑，要么降难度；`API.md` 第 4 节有降级规则 |
| `[[]]` 双链点开是空笔记 | 生成了知识库里不存在的概念名 | 用 Obsidian 反链面板核对；缺的笔记用 `tech-concept-deep-dive` 补，或改成普通文本 |
| 阶段划分看着合理，但每阶段都跑不起来 | 阶段产物只有"文件清单"，没有"可运行状态" | 每阶段补一条"产物 + 一条可执行验证" |
| 技术选型只列名字，没有理由 | 没要求对比 | 每层加"替代方案 + 为什么不选"；写不出替代方案说明这块没想清楚 |
| 交给 `project-scaffolder` 后生成的指南和方案脱节 | 交接时只给了摘要 | 把 8 大部分**整体**交出去（见 `API.md` 第 5 节） |
| 扩展方案与现有代码冲突 | 没先做事实核查 | 先让 `project-processization` 核对现有实现，再出扩展方案 |

## 2. 三种典型"假合格"

识别它们比修 bug 更重要：

1. **清单合格**：质量清单 14 条全打勾，但抽查一个阶段跑不通——说明清单被当成填表，没被当成约束。
2. **术语合格**：满篇 RAG、向量检索、RRF，但没一处说明"为什么用 RRF 而不是加权求和"。
3. **结构合格**：8 部分齐全，但第五部分每阶段只有 3 行——结构对了，内容空了。

对应验法都在 `TESTING.md`：②抓占位符、③抓双链、④抓验收可执行性、第五节"抽样做 30 分钟"抓最致命的第三种。

## 3. 定位"哪一部分坏了"

```bash
# 各部分行数占比——某部分显著偏短就是可疑对象
awk '/^## /{if(h)print h": "n; h=$0; n=0; next}{n++} END{print h": "n}' plan.md
```

经验值：五（分步教程）应占全文 30% 以上；六（验收）不低于 10%。二、三、四过短说明设计没展开。

## 4. 回滚与重来

方案不满意时，**不要在原文档上打补丁**（越改越像缝合怪）。正确做法：

1. 明确是"某一部分不合格"还是"整体方向不对"；
2. 前者：只重生成该部分，并要求与其余部分对齐；
3. 后者：保留已确认的需求与技术栈，从头生成一次，旧方案留档对比。

## 5. 什么时候该放弃本 Skill

- 用户其实想要**可运行代码** → 直接用 `project-scaffolder`；
- 项目**已经存在**，要的是读懂它 → `project-processization`；
- 用户还没选定方向 → 先 `learning-path-planner`，别在方案层反复试错。
