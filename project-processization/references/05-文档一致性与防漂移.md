# 文档一致性与防漂移（写完只是开始）

> 事实核查解决"写的时候对不对"；本文件解决**"写完以后还对不对"**。
> 经验来源：一个真实项目的学习指南在 24 小时内被改了 6 轮，其中 4 处数字/路径/接口
> 在代码变更后失真，而当时所有"生成时校验"都是绿的。

## 目录

## 1. 漂移是怎么发生的

三个条件同时成立就会漂移，缺一不可：

| 条件 | 典型表现 |
|---|---|
| 文档与代码不在同一处 | 文档在私人笔记区，改代码时看不到 |
| 没有触发点 | 没有"改接口必须改文档"的流程 |
| 没有自动校验 | 错了没人报警，直到面试官问起 |

**错误认知**："我写的时候核对过源码，所以是对的。"——写的时候对，不等于一周后还对。

真实案例（同一项目内）：

- 文档写评测字段 `hit_at_k`，代码返回 `hit@k` → 前端接出 `undefined`；
- README 写 79 个测试，实际已 105 个；
- 部署文档写 `/opt/xx/产品/backend`，仓库早已拆成独立仓；
- 架构图把"图谱能力"画进主检索链路，代码里是旁路；
- 能力清单写"A2A 支持互操作"，实际默认关闭且要令牌。

## 2. 第一原则：单一事实源

**能自动生成的，绝不手写。**

| 事实 | 事实源 | 做法 |
|---|---|---|
| 接口清单与字段 | OpenAPI（`app.openapi()`） | 生成 `openapi.json` 后再写文档，或直接从它取路径做断言 |
| 环境变量 | `config.py` / `.env.example` | 从配置类导出表格，别手抄 |
| 测试数量 | `pytest --collect-only` 或 AST 统计 | 由脚本比对，不靠记 |
| 依赖版本 | 锁文件 | 文档只写"主版本 + 用途"，不抄版本号 |
| 表结构 | 迁移文件 / ORM 模型 | 文档写"13 张表"这类结论，明细指向迁移 |

判断标准一句话：**换个解释器（换个人、换台机器、换个模型）还对得上吗？** 对不上就该交给脚本。

## 3. 四类断言（`check_docs.py`）

`scripts/check_docs.py` 把最容易漂移的四类事实变成断言：

| 检查 | 判据 | 常见误报与处理 |
|---|---|---|
| 测试数量 | 文档 `N passed` / `N 个测试` vs AST 统计 | 前端 `npm run test # 5 passed` 要排除；skip 用例单独计数 |
| 文档路径 | 反引号里 `backend/` `frontend/` `docker/` `.github/` 路径必须存在 | `scripts/xx.py` 可能指 `backend/scripts/xx.py`，做一次兼容 |
| 废弃表述 | 黑名单：旧目录名、旧字段名、旧数字 | 用 `--forbid` 追加，别把规则散落在文档里 |
| 私有文件 | `git ls-files` 里不得出现私有文档与 `.env` | 只查"已跟踪"，本地存在但被忽略的不算 |

用法：

```bash
python scripts/check_docs.py --root . --tests backend/tests
python scripts/check_docs.py --root . --openapi openapi.json --json
python scripts/check_docs.py --root . --forbid "旧路径/" --private "内部复盘.md"
```

**一条重要经验**：先做反向验证——故意塞一个假路径/假数字，确认脚本真的会红。
只看它输出 OK，等于没验证。

## 4. 接入 CI：让漂移变红

放在 lint job 里，成本约 2 秒：

```yaml
      - name: Docs consistency
        run: python scripts/check_docs.py --root . --tests backend/tests
```

> 需要完整的四道门（lint / test / build / 镜像）片段与六个常见坑，见 `project-scaffolder/references/ci-snippets.md`（若已安装该 Skill；未安装时按本节做法逐项补即可）。

没有 CI 时的最低要求：**交付前手动跑一次，并把输出贴进交付说明**（有输出的才算验证过）。

## 5. 架构图规范：图必须能指到函数

图画错的代价比没图更大——面试官会顺着图问。

| 规范 | 说明 |
|---|---|
| 每层标真实入口 | 写 `rag_service.retrieve()`、`get_db`、`FETCH_K=20`，而不是"检索模块" |
| 线型即语义 | 实线 = 用户请求真正走的路径；虚线 = 已实现但未接入 |
| 未接线必须显式 | 旁路能力画虚线框并注"未接入主链路"，别画成主链路的一环 |
| 版本化 | 文件名带 `-v3`/`-v4`，文首标日期；旧图归档但注明"别引用" |
| 改代码就升版 | 主链路、数据流、外部依赖任一变化，图必须跟着变；不升版等于埋雷 |

**自检一句话**：指着图上任意一个方框，你能说出对应哪个文件/函数吗？说不出就是画错了。

## 6. "假完备"清单：看起来有、实际没用

比"没做"更危险的是"看起来做了"。交付前逐项确认：

| 类型 | 症状 | 确认方法 |
|---|---|---|
| 死配置 | 配置项存在但没人读 | `grep 配置名` 全仓，只有定义处 = 死配置 |
| 零调用模块 | `cache.py` 写好了但无人 import | `grep "import cache"` |
| 假 TTL | `set(key, v, ttl=...)` 的 ttl 参数没实现 | 写一条"等 2 秒再取"的用例 |
| 未接线能力 | 接口在、页面在，但主链路不经过 | 从入口函数顺调用链，看是否分支 |
| 未生效开关 | 开关改了行为不变 | 改开关跑一次，对比输出 |

文档里对这类能力要标三态：**已接线 / 旁路可用 / 未生效**，不能统一写成"支持"。

## 7. 公开 / 私密分离（安全边界）

学习指南里必然有"哪些是 AI 写的、你该补什么"，这类内容**不能给面试官看**。
所以产物必须是两份，而不是一份：

| 文档 | 受众 | 内容 | 位置 |
|---|---|---|---|
| `README.md` | 面试官 / 使用者 | 能力、用法、架构、限制、测试与 CI | 项目仓库 |
| `项目学习指导书.md` | 你自己 | 分工、AI 协作比例、逐章精读、验收与练习 | **仓库外**（如项目仓外的 `../private-notes/`） |

四条硬规则：

1. 仓库里只放"能给面试官看"的内容；
2. 私有文档路径写进 `.gitignore`；
3. `check_docs.py` 的私有文件检查作为 CI 守卫（`git ls-files` 一旦出现即红）；
4. **不要用 `git add -A`** 盲加——这是私有文档误入仓库的头号入口，先 `git status` 看一眼。

> 真实事故：一次 `git add -A` 把 10 万字的私有指导书提交并推到了公开仓库，
> 处置需要 `git rm --cached` + `git filter-branch` 重写全部历史 + 强制推送。
> 防复发靠的不是"下次注意"，是 `.gitignore` + CI 断言。

## 8. 交付前 checklist

- [ ] `check_docs.py` 全绿，且做过一次**反向验证**（假输入会红）
- [ ] 脚本已进 CI（或至少在交付说明里贴了输出）
- [ ] 架构图每层能指到具体文件/函数；未接线能力用虚线标注
- [ ] 图与代码版本一致；旧图已归档并注明
- [ ] 能力清单区分"已接线 / 旁路 / 未生效"
- [ ] 私有文档不在仓库；`.gitignore` 已含；CI 守卫生效
- [ ] 所有"已完成"的表述后面都有可复现的命令或数字
