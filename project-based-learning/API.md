# API

本 Skill 没有可执行接口，这里的"API"指**输入契约与输出契约**——说清给什么、拿什么、边界在哪。

## 1. 输入契约

### 必填

| 字段 | 说明 | 缺失后果 |
|---|---|---|
| 项目主题 | 一句话说明做什么（"RAG 知识库问答"） | 无法确定项目类型，方案会退化为通用模板 |
| 学习目标 | 想练哪些技术点（"练向量检索与重排"） | 选型与分步教程失去针对性 |

### 选填（有默认值）

| 字段 | 默认 | 备注 |
|---|---|---|
| 项目类型 | 由主题推断 8 类之一 | 见 `references/project-types-and-templates.md` |
| 技术栈 | 该类型的通用组合 | **建议显式给出**，否则选型章节只能给对比、无法给决断 |
| 难度 | ⭐⭐⭐ | 与周期联动：入门 ⭐⭐ / 2–3 周 |
| 周期 | 4 周 | 超过 8 周需拆分里程碑，否则方案不可执行 |
| 知识库联动 | 开启 | 关闭后不产出 `[[]]` 双链 |
| 是否已有项目 | 否 | 是则走"扩展方案"分支 |

## 2. 输出契约

固定 8 大部分，顺序不变；每部分的**必填字段**如下（模板见 `references/project-templates.md`）：

| # | 部分 | 必填字段 |
|---|---|---|
| 一 | 项目概述 | 名称、类型、难度、周期、技术栈、最终产物、学习目标 |
| 二 | 需求文档 | 功能表（含优先级 P0/P1）、非功能指标（含数字）、用户故事 |
| 三 | 技术选型 | 每层方案、选择理由、与替代方案对比、对应知识库笔记 |
| 四 | 架构设计 | 架构图、目录结构、表结构、API 契约 |
| 五 | 分步实现教程 | 阶段划分、每步目标、代码要点、阶段产物、阶段验收、`[[]]` 双链 |
| 六 | 验收标准 | 功能/性能/质量/部署四类，每条 = 命令 + 期望输出 |
| 七 | 扩展方向 | 具体改动 + 解决的问题 + 前置条件 |
| 八 | 学习资源 | 官方文档链接、关键概念、常见坑 |

### 硬性约束

1. 每部分必须有实质内容，**不允许出现"待补充""XXX 技术"这类占位符**；
2. 每条验收必须可复制执行，并给出可判定的期望输出；
3. 技术概念首次出现处加 `[[]]` 双链（联动关闭时除外）；
4. 代码片段只作为**教程里的示例**，不构成完整项目；完整项目由 `project-scaffolder` 产出。

## 3. 边界（不做什么）

| 不做 | 替代 |
|---|---|
| 生成可运行项目骨架 | `project-scaffolder` |
| 对已有代码做事实核查 / 精读 | `project-processization` |
| 替用户决定做哪个项目 | `learning-path-planner` |
| 评估用户当前水平 | 由用户自述难度；本 Skill 不测水平 |

## 4. 失败与降级

| 情况 | 行为 |
|---|---|
| 主题过于笼统（"做个项目练手"） | 追问一次类型与技术栈；仍不明确则给 3 个候选方向，不硬生成 8 部分 |
| 周期 < 2 周 | 提示范围过大，建议降级为"单点练习项目"或延长周期 |
| 技术栈自相矛盾（Vue2 + Vite） | 指出冲突并给替代组合，不静默择一 |
| 与已有项目重叠 | 提示改走"扩展方案"分支，避免重复造轮子 |

## 5. 与下游 Skill 的接口

```
project-based-learning（8 大部分）
        │  第一部分~第四部分 → 直接作为需求与架构输入
        ▼
project-scaffolder（生成项目 + 分工指南）
        │  项目落地后
        ▼
project-processization（事实核查 + 精读指南 + 验收清单）
```

交给 `project-scaffolder` 时，**把 8 大部分整体交出去**，不要只给一句话摘要——摘要会丢掉验收标准与阶段划分，导致生成的行动指南重新做一遍规划。
