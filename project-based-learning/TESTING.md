# TESTING

本 Skill 没有代码，**测试对象是生成的方案**。目标是：用可复制的命令，判断一份方案是"能落地的设计"还是"漂亮的模板"。

## 1. 七条可执行抽查

把生成的方案存成 `plan.md` 后逐条跑。

```bash
# ① 结构完整性：8 个一级部分是否都在
grep -cE '^## (一|二|三|四|五|六|七|八)、' plan.md        # 期望 8

# ② 占位符残留：模板词没有被替换
grep -nE 'XXX|待补充|TBD|\.\.\.$' plan.md | head            # 期望无输出

# ③ 知识库双链：按“出现次数”数，不是行数
grep -o '\[\[' plan.md | wc -l                              # 期望 ≥ 阶段数（每阶段至少 1 个）

# ④ 验收可执行性：第六部分里的命令行或行内代码
awk '/^## 六、/,/^## 七、/' plan.md | grep -cE '^[[:space:]]*(curl|python|pytest|npm|docker|wrk|ab|make) |`[^`]+`'   # 期望 ≥ 验收条目数

# ⑤ 选型对比：第三部分是否出现对比/替代/不选
awk '/^## 三、/,/^## 四、/' plan.md | grep -cE '不选|替代|对比|为什么不'   # 期望 ≥ 1；每条选型都要能说出替代方案

# ⑥ 分工与卡片：按“出现次数”数
grep -o 'AI 可代劳' plan.md | wc -l                          # 期望 ≥ 阶段数
grep -o '动手卡片' plan.md | wc -l                            # 期望 ≥ 阶段数

# ⑦ 估计值与命令安全：估计值有标注、没有无条件覆盖 .env
grep -nE '估计|预计' plan.md | head                          # 期望能看到周期/性能的"估计"说明
grep -nE '^[[:space:]]*cp .*\.env' plan.md                   # 期望无输出；有则必须是条件复制
```

阈值不是硬指标，是**报警线**：②命中即不合格；③⑥按**出现次数**计，示例骨架（1 个阶段）应至少各 1 次；④⑤低于预期说明方案退化成清单。

## 2. 人工判断的三件事

| 检查 | 不合格的样子 | 合格的样子 |
|---|---|---|
| 难度与周期匹配 | ⭐⭐⭐⭐ 微服务 + 3 周 | ⭐⭐⭐⭐ 拆成 2 个里程碑，或降到 ⭐⭐⭐ |
| 阶段产物可运行 | "阶段一：搭好项目结构"（跑不起来） | "阶段一产物：`/health` 返回 `{"status":"ok"}`" |
| 扩展方向具体 | "可以加缓存优化性能" | "热点文章加 Redis 缓存，读 QPS 从 200 提到 800" |

## 3. 抽样验证（最重要的一条）

挑方案里的**一个阶段**，照它做 30 分钟：

- 能跑通 → 教程至少没硬伤；
- 卡住 → 卡点是缺依赖、缺文件还是缺说明？把卡点记下来，这类缺陷靠读是发现不了的。

一个阶段都跑不通的方案，8 部分写得再整齐也不能用。

## 4. 回归：改模板之后

修改 `references/` 或 `SKILL.md` 的 8 部分表后，必须做：

1. 用同一个输入（如"RAG 问答，4 周，FastAPI + Chroma"）重新生成一次；
2. 对比新旧方案：**结构是否仍然 8 部分、验收是否仍可执行、双链是否仍存在**；
3. 若某个部分变短，确认是"信息密度提高"而非"内容丢失"。

## 5. 已知盲区

- **无法验证技术判断的对错**：方案说"用 Chroma 而不是 Milvus"，本 Skill 不判断这个结论是否正确，只判断它有没有给理由。
- **无法验证知识库笔记是否真实存在**（除非用户提供笔记清单）：新规则要求链接到主题并标「待建」，但仍需在 Obsidian 侧用反链检查。
- **周期估算无基线**：4 周是经验值，不因个人水平自适应；方案必须写清"按每周 15-20 小时估"的假设。
