# 项目全周期生成器（Project Scaffolder）

> 你说"我想做一个 XX 项目"，本 Skill 自动完成：需求分析 → 资源选型 → 生成全部产物 → 人机分工 → 指导文档 → 多轮自检。
>
> **不限代码项目**：软件、学习、内容、商业、研究、活动、个人生活，以及混合型项目都能处理。

---

## 核心理念

- **AI 负责**：能被结构化、标准化、信息整合、有方法论的所有工作
- **用户负责**：物理行动、真实社交、个人决策、个性化输入、承担后果
- **关键原则**：AI 负责"造"，用户负责"懂、用、练"

---

## 触发条件

**触发**：
- "我想做一个 XX 项目" / "帮我规划/搭建一个 XX"
- "从零开始做 XX" / "帮我生成 XX"
- "我要完成 XX，帮我"
- 任何描述了"需要多步骤、多产物才能完成的目标"的请求

**不触发**：
- 单一简单任务（翻译、写邮件、改一句话）→ 直接完成
- 纯闲聊、事实查询

---

## 工作流程（严格按顺序执行）

### 第一步：项目识别与需求分析

1. **判断项目类型**（可多选，多数项目是混合型）。7 大类型的特征、产物清单、章节适配、验收标准详见 [references/project-types.md](references/project-types.md)。

2. **确认或推断**：
   - 项目目标（做完要达到什么效果）
   - 成功标准（怎样算完成，可衡量）
   - 约束条件（时间、预算、人力、资源、环境）
   - 当前基础（用户水平、已有资源）
   - 关键风险（可能卡住/失败的地方）

3. **需求不明确时**：
   - 缺关键信息且影响产物方向 → 一次追问完（不超过 4 个问题）
   - 不影响整体方向 → 先做合理假设并标注，后续可调整

4. **输出**：
   - 项目定位说明（一句话 + 一段话）
   - 项目类型标注（主类型 + 混合类型）
   - 成功标准清单（可打勾）
   - 约束与风险清单

### 第二步：产物规划与资源选型

1. **工作分解结构（WBS）**：列出完整产物清单，每个产物说明：名称、格式、作用、所属阶段、依赖关系。

2. **功能完整性矩阵**（所有项目必做，防止"只做核心功能、遗漏周边标配"）：
   - 确定项目类型后，立即查阅 [references/content-completeness.md](references/content-completeness.md) 对应类型的"标配功能清单"
   - 在 WBS 中列出所有核心功能（P0）和周边标配功能（P1），标注优先级
   - 对于不适用的功能，明确说明"本项目不包含 XX，因为 XX"
   - **禁止**：只列核心功能，忽略收藏/搜索/通知/互动等周边标配功能
   - 示例：社交平台不能只做"发图+点赞"，必须同步规划收藏、搜索、通知、评论点赞、个人主页美化等 P1 功能

3. **资源/工具选型**（不限软件，按项目类型）：
   - 软件：开发框架、数据库、部署平台
   - 学习：教材、课程、练习工具、社区
   - 内容：创作工具、发布平台、素材来源
   - 商业：获客渠道、支付工具、协作平台
   - 研究：数据库、文献来源、分析工具
   - 活动：场地、供应商、宣传渠道
   - **技术选型必须有决策依据**（软件类项目必做）：不得随意选择框架，必须按 [references/tech-selection.md](references/tech-selection.md) 的决策框架，从"项目需求→约束条件→候选对比→最终选型"四步推导，并在文档中说明选型理由

4. **项目结构规划**：
   - 文件型项目：输出完整目录/文件树
   - 线下/混合型：输出"模块/环节/任务"结构树
   - 标注每个部分的负责人（AI 或 用户）

5. **依赖关系**：输出产物依赖关系图（Mermaid 或流程清单），识别可并行/必须串行的部分。

### 第三步：产物生成（AI 直接完成的部分）

1. **生成所有 A 类产物**（分工标准见第四步）：
   - 必须完整、可直接使用，不允许"省略部分内容""其余类似"
   - 代码类：完整可运行，含注释
   - 文档类：结构完整，内容可直接使用
   - 计划类：具体到时间、任务、责任人、验收标准
   - 模板类：含填写说明和示例
   - 清单类：可直接打勾使用

2. **各类型项目的 A 类产物参考**详见 [references/project-types.md](references/project-types.md)。

3. **生成 B 类产物的框架**：
   - 先生成结构和示例
   - 明确标注每个需要填写的位置：填什么、怎么填、填的标准
   - 提供示例答案（用户可参考或替换）

4. **生成质量强制约束**（代码类项目必做，在生成时就遵守，不要等到第六步自检才发现）：
   - **前后端同步生成**：先生成后端路由和请求/响应 schema，再基于后端 schema 生成前端 API 封装，确保字段名、URL、HTTP 方法完全一致；禁止先写前端再猜后端接口
   - **静态资源同步生成**：代码中引用的每一个静态资源（图片、图标、字体）必须在生成代码的同时生成对应占位文件；配置文件中引用的资源（如 tabBar 图标、favicon）也必须同步生成
   - **框架语法实时遵守**：生成代码时就遵守目标框架的语法约束（如小程序 WXML 不能调用 JS 函数、React JSX 不能用 if/for），不要生成违反框架规则的代码再靠自检修复
   - **实时通信必须带认证**：生成 WebSocket/SSE 等实时通信端点时，必须同时实现 token 认证机制（query 参数传 token 或连接后首条消息认证），禁止生成无认证的实时端点
   - **前端空值安全访问**：访问全局状态（如 `app.globalData.userInfo`）时必须用安全访问模式（`userInfo && userInfo.id` 或可选链），禁止直接 `userInfo.id` 导致未登录时崩溃
   - **核心功能同步生成测试**：生成后端路由时，为核心路由（认证、CRUD、业务逻辑）同步生成 pytest 测试文件；测试应覆盖正常流程和边界情况
   - **新增功能必须同步更新文档**：每次新增/修改功能模块后，必须同步更新 README.md（技术栈/功能列表/页面数/模型数）和《项目全景总结与行动指南》（总览表/分工说明/操作指引），禁止出现"代码已更新但文档还写旧内容"
   - **周边标配功能同步生成**（所有项目必做）：生成核心功能时，必须对照 [references/content-completeness.md](references/content-completeness.md) 的标配功能清单，同步生成 P1 级周边功能；周边功能不是"后续迭代"，而是"首次交付就包含"；每个周边功能必须完整实现（后端+前端+数据模型），不允许"留空"或"TODO"；示例：社交平台生成"发图+点赞"时，必须同步生成收藏、搜索、通知、评论点赞、个人主页等周边功能
   - **工程底座六件套同步生成**（代码类项目必做）：版本化 schema（Alembic）/ 索引 / CI 质量门 / 文档断言 / 私有边界 / 生产默认安全。这六项是 P0，不是"后续优化"，详见 [references/engineering-baseline.md](references/engineering-baseline.md)；缺任何一项，项目在"改结构、上生产、被追问"时必翻车
   - **文档断言同步生成**：生成 README 的同时准备 `scripts/check_docs.py`（测试数、路径、废弃表述、私有文件四类断言）并接入 CI。脚本来源按优先级：
     1. **已安装 `project-processization`**：直接从其 `scripts/check_docs.py` 复制到项目（**同源，禁止改逻辑**）；
     2. **未安装**：按 [references/engineering-baseline.md](references/engineering-baseline.md) 3.4 节自实现最小版（四类断言约 80 行）。
     **禁止两个位置各维护一份**——两份必然漂移，这正是本项目要防的问题。
   - **私有/公开边界同步生成**：任何含"AI 已完成比例、分工说明、内部复盘"的文档默认视为私有，写入 `.gitignore` 并放在仓外；`.env`、数据库文件、上传目录一并忽略
   - **禁止假完备**：不允许生成"配置项存在但无人读取""模块写好但零调用""TTL 参数未实现""接口在但主链路不经过"的代码。要么接线，要么明确标注"旁路可用"，不要让它看起来在工作
   - **测试必须可复现**：假数据/假向量不能用内置 `hash()`（受 `PYTHONHASHSEED` 影响，跨进程不稳定），改用 `crc32` 之类稳定哈希；按 id 落盘的索引/缓存要在用例间清理，避免互相污染

### 第四步：人机分工判断（核心环节）

对项目的每个环节、每个产物，判断属于 A/B/C 哪一类。

**通用判断三问（按顺序）**：
1. "这个动作 AI 能不依赖用户、独立完成吗？" → 能 = **A**
2. "AI 能完成大部分，但需要用户补充个人信息或做最终确认吗？" → 是 = **B**
3. "这个动作需要物理世界参与、真实社交、资金/法律操作，或必须由用户亲自体验吗？" → 是 = **C**

**分工输出要求**：
- 输出完整人机分工表：每个产物/环节标注 A/B/C
- C 类任务必须给出：为什么 AI 不能替你做、你需要做什么、怎么验证做完了
- B 类任务必须给出：AI 已做好的框架、用户需要填什么、填写标准和示例

A/B/C 类的完整特征、典型示例、7 类项目的具体分工示例详见 [references/division-rules.md](references/division-rules.md)。

### 第五步：生成《项目全景总结与行动指南》

这是 Skill 的核心指导文档。

**文档结构**：
1. 开头：Frontmatter + 项目定位 + 资源全景表 + 学习路线总览（三篇递进）+ 🤝全章分工总览表 + 核心原则
2. 正文：三篇递进
   - **入门篇：准备与启动**（目标：跑通/启动）
   - **进阶篇：核心模块构建**（目标：理解原理/掌握核心）
   - **实战篇：落地与优化**（目标：真实可用/求职/交付）
3. 末尾：速查表 + 配置/资源说明 + 常见问题/面试题（至少8道）+ 风险排查 + 进阶资源 + 结语

**每章必须包含七要素**：
1. 概念解释（定义 + 生活化比喻 + 核心价值）
2. 原理说明（机制 + 设计原因 + 对比 + 可视化）
3. 操作指引（步骤 + 预期结果 + 坑点）
4. 🤝 本章分工（🤖 AI 已完成 + 👤 你需要做 + B类填空指引/C类验证方法）
5. 💡 本章深度讲解（3-5 句）
6. 📝 本章精简总结（要点列表）
7. 🎯 梯度验证任务（基础⭐ + 进阶⭐⭐ + 实战⭐⭐⭐）

**规模适配规则**：
- 小型项目（1-3 天）：精简为 1 篇，3-6 章
- 中型项目（1-4 周）：标准三篇，每篇 3-8 章
- 大型项目（1 个月以上）：完整三篇，可拆分阶段，每阶段独立指导文档

完整的文档模板（含各项目类型适配、七要素详细写法、各篇章验收清单）详见 [references/doc-template.md](references/doc-template.md)。

### 第六步：多轮自检与交付

按以下十二个维度自检，输出自检报告，全部通过后交付；有问题立即修复并重新自检：

**基础维度（文件与文档）**

1. **产物自检**：文件完整、可打开、可使用；依赖/资源齐全；入口明确；产物间一致
2. **文档自检**：每章七要素完整；人机分工清晰；可视化准确；标题/代码块/Frontmatter 规范
3. **分工自检**：每个产物标注 A/B/C；C 类有验证方法；B 类有填空指引；无错判漏判
4. **通用性自检**：流程适配不同项目类型；无代码专属表述未泛化；非文件型产物有管理方式
5. **可执行性自检**：用户拿到后能按文档启动、操作、验收；无跳步、无悬空指引

**深度维度（防止"文件存在但跑不通"）**

6. **前后端契约检查**（含前端/API 类项目必做）：
   - 前端调用的每个 API 端点（URL + HTTP 方法）必须在后端路由中存在
   - 前端传的字段名（request body / query / form）必须与后端接收的参数名一致
   - 后端返回的字段名必须与前端读取的字段名一致
   - 上传类接口：确认前端传的是文件还是URL字符串，后端接收方式必须匹配
   - **功能完整性反向检查**：列出后端所有 API 端点，确认每个核心端点（非内部/调试用）都有对应的前端调用或文档说明；禁止出现"后端实现了推荐/私信等功能但前端完全没接入"的情况
   - 检查方法：列出前端所有 API 调用，逐条与后端路由比对；再列出后端所有路由，逐条确认前端是否接入

7. **依赖完整性检查**（含代码类项目必做）：
   - 扫描所有代码文件的 import / require / from 语句
   - 确认每个第三方依赖都在依赖清单（requirements.txt / package.json / pom.xml 等）中声明
   - 确认依赖清单中没有未使用的包（减少体积）
   - 确认标准库和本地模块不需要加入依赖清单
   - 检查方法：用脚本提取所有 import，与依赖清单比对

8. **静态资源检查**（含前端/UI 类项目必做）：
   - 扫描所有代码中引用的静态资源路径（图片、图标、字体、音频等）
   - 确认每个被引用的资源文件实际存在于项目目录中
   - 确认资源路径的大小写与实际文件名一致（Linux 服务器大小写敏感）
   - 配置文件中引用的资源（如 app.json 的 tabBar 图标、index.html 的 favicon）也要检查
   - 缺失的资源必须生成占位文件或修改引用

9. **框架语法检查**（含代码类项目必做）：
   - 针对使用的框架，检查该框架的特定语法约束：
     - **微信小程序**：WXML 中不能调用 JS 函数（必须在 data 中预处理）；WXML 中不能访问 JS 模块对象；页面必须在 app.json 中注册；tabBar 图标文件必须存在
     - **React**：JSX 中不能使用 if/for 语句（必须用三元/map）；组件名必须大写；useEffect 依赖数组必须完整；不能在条件中调用 Hook
     - **Vue**：模板中不能调用未在 setup/data 中暴露的变量；v-for 必须有 key；computed 不能有副作用
     - **Next.js**：页面组件必须在 pages/ 或 app/ 目录；服务端组件不能使用浏览器 API（window/document）；getServerSideProps/getStaticProps 只能在页面组件中使用
     - **Nuxt**：页面组件必须在 pages/ 目录；asyncData/fetch 只能在页面组件中使用；不能在客户端访问 process.server
     - **Angular**：组件必须在 NgModule 中声明；@Input/@Output 必须有类型；不能在构造函数中访问 @ViewChild
     - **FastAPI**：路由参数类型必须与函数签名一致；依赖注入参数必须有默认值或 Depends；async 路由函数不能调用同步阻塞操作
     - **Flask**：路由函数必须返回 Response 或可转换为 Response 的对象；不能在请求上下文外使用 request/g；蓝图必须注册到 app
     - **Django**：model 字段必须在 migrations 中体现；URL 名必须与 reverse 匹配；视图必须返回 HttpResponse
     - **Spring Boot**：@Controller/@RestController 必须被 @ComponentScan 扫描；@Autowired 字段不能是 final（除非使用构造器注入）；@Transactional 不能在同类内部调用
     - **Express**：中间件必须调用 next() 或发送响应；错误处理中间件必须有 4 个参数；不能在响应发送后再设置 header
     - **Flutter**：Widget 必须是不可变的（所有字段 final）；build 方法不能有副作用；StatefulWidget 的 State 必须正确 dispose 控制器
     - **uni-app**：页面必须在 pages.json 中注册；条件编译 #ifdef 必须正确闭合；不能在 App.vue 中使用页面生命周期
   - 检查方法：根据项目使用的框架，逐条核对框架特定规则

10. **运行时验证**（所有项目必做，防止"静态全过但跑不起来"）：
    - **代码项目**：
      - 后端：尝试 `python -c "from app.main import app"`（Python）或 `npm run build`（Node）或 `mvn compile`（Java），确认无导入错误和编译错误
      - 前端：尝试 `npm run build` 或 `npm run compile`，确认无编译错误；小程序项目检查 app.json 页面注册与实际文件一致
      - 数据库：确认所有模型都能被 ORM 识别（导入所有模型文件），表名和字段名无冲突
    - **配置项目**：
      - YAML/JSON/TOML 配置文件必须能被解析器正确解析（无语法错误）
      - 环境变量模板（.env.example）中的变量名必须与代码中读取的变量名一致
      - Dockerfile 必须能通过 `docker build --no-cache` 构建（如条件允许）
    - **文档项目**：
      - Markdown 链接必须指向存在的文件或有效 URL（无死链）
      - 代码块中的命令必须可执行（路径正确、参数有效）
      - 目录结构描述必须与实际生成的文件一致
      - **文档与代码一致性**（代码类项目必做）：README.md 中的技术栈/功能列表/页面数/模型数必须与实际代码一致；指导文档中的"AI 已完成 vs 你需要做"分工必须与实际产物一致；新增功能后必须同步更新 README 和指导文档，禁止出现"文档写8个页面但实际有9个"这类过时内容
    - **学习/计划项目**：
      - 时间表中的日期必须合理（无矛盾、无过去日期）
      - 任务分解必须可执行（每个任务有明确的完成标准）
      - 资源链接必须可访问
    - **检查方法**：用脚本或命令实际执行，不依赖"看起来没问题"的判断；运行失败必须修复后重新验证

11. **内容完整性检查**（所有项目必做，防止"核心功能有但周边功能缺失"）：
    - 对照 [references/content-completeness.md](references/content-completeness.md) 中对应项目类型的"标配功能清单"，逐项检查是否已实现
    - **P0 功能**：必须全部实现，缺失即为不通过
    - **P1 功能**：必须全部实现或明确说明不适用的原因，缺失且无说明即为不通过
    - **P2 功能**：可标注为"后续扩展方向"，不强制实现
    - **功能完整性反向检查**：列出所有已实现的 API 端点/功能模块，确认每个都有对应的用户入口（页面/按钮/菜单）或文档说明；禁止出现"后端实现了通知/推荐等功能但前端完全没有入口"的情况
    - **常见缺失模式**（重点检查）：
      - 社交/内容类：有发布但没收藏、有列表但没搜索、有互动但没通知、有评论但没评论点赞、有个人主页但信息展示不完整
      - 电商类：有商品但没搜索/筛选、有下单但没订单列表、有用户但没收货地址管理
      - 工具类：有核心功能但没数据管理（列表/编辑/删除）、没搜索/筛选
      - 学习类：有知识点但没练习题、有计划但没进度跟踪
    - 检查方法：先列功能清单 → 逐项核对实现状态 → 对缺失项判断是 P0/P1/P2 → P0/P1 缺失必须修复或说明

**工程维度（能否长期维护）**

12. **工程底座与文档一致性检查**（代码类项目必做）：
    - **迁移可执行**：空库跑 `alembic upgrade head` 能建全；老库能通过 `stamp` 纳管；迁移本身有用例
    - **索引有效**：高频查询的 `EXPLAIN` 是 `SEARCH` 而非 `SCAN`，无 `USE TEMP B-TREE FOR ORDER BY`
    - **质量门可跑**：lint / test / build / docker 四门在 CI 中全绿；测试命令用 `python -m pytest`（console script 不会把 CWD 加进 `sys.path`）
    - **文档断言生效**：`check_docs.py` 在 CI 里，且做过反向验证（写错数字会红）
    - **私有边界干净**：`git ls-files` 中无私有文档与 `.env`；`.gitignore` 覆盖
    - **默认安全**：`AUTO_CREATE_TABLES=false`；互操作/危险工具默认关闭
    - **无假完备**：`grep` 确认无死配置、零调用模块、假 TTL、未接线能力
    - **一键自检**：`python scripts/check_baseline.py --root .` 覆盖上述七项（schema/index/ci/docs/private/defaults/deadconfig），有 error 即非零退出，可接 CI

### 第七步：Git 初始化与交付

所有产物生成并通过自检后，初始化版本控制并交付：

1. **生成 .gitignore**（代码类项目必做）：
   - Python：`__pycache__/`、`*.pyc`、`*.pyo`、`.venv/`、`venv/`、`*.db`、`.env`、`uploads/`
   - Node：`node_modules/`、`dist/`、`.next/`、`.nuxt/`、`.env.local`
   - 通用：`.DS_Store`、`Thumbs.db`、`*.log`、`.idea/`、`.vscode/`
   - **私有文档**：`项目学习指导书.md`、`内部复盘.md` 等含分工/AI 协作说明的文件必须忽略
   - 根据项目类型生成对应的 .gitignore，不使用万能模板

2. **初始化 Git 仓库**（如项目目录尚未是 Git 仓库）：
   ```bash
   git init
   git status --short          # 先看清楚再 add，禁止盲加
   git add .
   git commit -m "feat: 初始化项目 - <项目名称>"
   ```
   - **禁止不检查就 `git add -A`**：这是私有文档/密钥误入公开仓库的头号入口
   - 提交前确认：`git ls-files | grep -i "指导书\|\.env$"` 应无输出
   - 如已是 Git 仓库，则先 `git status --short` 确认范围再 `git add . && git commit`
   - 提交信息遵循 Conventional Commits 规范（feat/fix/docs/refactor/test/chore）

3. **创建 README.md**（如项目类型适合）：
   - 项目名称 + 一句话描述
   - 技术栈/资源清单
   - 快速开始（安装、启动、使用）
   - 项目结构说明
   - 《项目全景总结与行动指南》链接

4. **交付清单确认**：
   - 所有产物文件已生成且通过自检
   - .gitignore 已生成且忽略规则正确
   - **README.md 与实际代码一致**：技术栈/功能列表/页面数/模型数/目录结构必须与实际生成的代码完全匹配（提交前最后一道验证，禁止带着过时的 README 提交）
   - **指导文档与实际产物一致**：总览表中的章节数、AI 已完成的产物列表、你需要做的任务清单必须与实际文件一致
   - Git 仓库已初始化且有初始提交
   - 《项目全景总结与行动指南》已放在项目根目录
   - 向用户说明：AI 已完成的部分、用户需要做的部分、下一步操作建议

## 配套脚本

`scripts/check_baseline.py`：把第 12 维自检变成可执行断言（纯标准库，无依赖）。

```bash
python scripts/check_baseline.py --root .            # 七项检查，error 时退出码 1
python scripts/check_baseline.py --root . --strict   # 警告也算失败
python scripts/check_baseline.py --root . --skip index,deadconfig --json
```

| 检查 | 判据 | 级别 |
|---|---|---|
| `schema` | 有迁移体系、版本文件非空、`create_all` 仅用于测试 | error/warn |
| `index` | 外键列是否带 `index=True`、是否有复合索引 | warn |
| `ci` | workflow 覆盖 lint/test/build；是否误用 console script `pytest` | error/warn |
| `docs` | `check_docs.py` 存在且接进 CI | warn |
| `private` | git 是否跟踪 `.env`/私有文档/数据库文件 | error |
| `defaults` | `AUTO_CREATE_TABLES` / `A2A_ENABLED` 默认值、令牌比较方式 | warn |
| `deadconfig` | 只定义未读取的配置项、TODO/NotImplemented | warn |

> **栈适用范围**：`schema` / `ci` / `docs` / `private` 与语言无关；`index` / `defaults` / `deadconfig`
> 依赖 Python 特征（SQLAlchemy 模型、`config.py`），非 Python 项目会输出"跳过：未发现 …"。
> **"跳过"不等于"通过"**——非 Python 栈实际只覆盖 4 项。
>
> 首次在已有项目上运行时，误报是正常的（例如测试里合法使用 `create_all`）。脚本按路径白名单跳过
> `tests/` `scripts/` `migrations/`；遇到其它误报，先判断"是不是真的可接受"，再决定调规则还是改代码。

## 增量更新与多轮迭代

> 首次生成后，用户几乎一定会要求修改、扩展或优化。本环节定义如何处理"已有项目的继续迭代"，这是实际使用中最常见的场景。

### 触发场景

- 用户说"继续优化""加一个功能""改一下 XX""这个地方有问题"
- 用户反馈运行错误、体验问题、需求变更
- 用户完成一个阶段后要求进入下一阶段
- 用户要求基于已有项目增加新模块

### 迭代流程（严格按顺序）

1. **现状探查**（必须先做，禁止凭记忆修改）：
   - 读取用户指定的文件，确认当前实际内容
   - 运行项目（如适用），复现用户描述的问题
   - 确认修改范围：只改用户点名的部分，不主动扩展

2. **影响评估**：
   - 修改会影响哪些其他文件/模块？
   - 是否需要同步更新文档（README/指导文档）？
   - 是否需要同步更新测试？
   - 风险等级：低（单文件修改）/中（多文件联动）/高（架构变更）

3. **执行修改**：
   - 只改被点名的范围，保留未要求改动的内容
   - 新增功能必须遵守第三步的生成质量约束（含工程底座六件套）
   - 修改后立即验证（运行测试/编译/手动检查）

4. **同步更新**：
   - 代码变更 → 同步更新 README（功能列表/页面数/模型数）
   - 功能变更 → 同步更新《项目全景总结与行动指南》（分工/操作指引）
   - 新增模型/路由 → 同步更新测试
   - **禁止**：只改代码不改文档

5. **验证与交付**：
   - 运行相关测试确认无回归
   - 运行第六步的相关自检维度（至少：前后端契约/运行时验证/文档与代码一致性）
   - Git 提交（遵循 Conventional Commits）
   - 向用户说明：改了什么、为什么这么改、如何验证

### 多轮自检（迭代后必做）

每次迭代修改后，至少运行以下 4 个维度的自检：
1. **前后端契约检查**：修改的 API 是否前后端一致
2. **运行时验证**：项目能否正常启动/编译
3. **文档与代码一致性**：README 和指导文档是否同步更新
4. **工程底座自检**（代码类项目）：`python scripts/check_baseline.py --root .` 无 error

详细的迭代指南（含常见迭代场景处理、回滚策略、版本管理）详见 [references/iteration-guide.md](references/iteration-guide.md)。

## 非文件型产物的管理方式

对于不产生文件的项目环节（习惯养成、谈判、练习、社交、决策）：
- 用 **行动清单 + 检查点 + 记录表** 管理
- 行动清单：具体做什么、频率、时长
- 检查点：什么时间验证、验证标准
- 记录表：可打印/可填写的记录模板
- 模板由 AI 生成（A 类），执行由用户完成（C 类）

## 输出规范

- 项目产物：直接写入用户指定的项目目录
- 指导文档：命名为《项目全景总结与行动指南.md》，放在项目根目录
- 所有 Markdown 符合渲染规范：
  - Frontmatter 严格 YAML（不在其中放代码块标记）
  - 代码块正确闭合（结束标记不带语言名，含嵌套时用 4 反引号）
  - 每篇恰好 1 个 H1，标题不跳级
  - 代码内容不暴露为标题
- 可视化数量按项目需要（中型项目建议至少 8 个），不机械凑数
- 产物命名清晰、结构自解释
