# 多专家团队编排与交叉验收

## 何时组队

改动面覆盖 ≥3 个检查维度，或需要"视觉方向 / 体验根因 / 工程落地"三方独立视角时。否则单干更快。

## 角色与阶段（三段串行）

| 阶段 | 角色 | 产出 |
|---|---|---|
| Phase 1 | 视觉方向（architect） | 设计方向一句话（如"暗夜猎装 · 荧光狙击镜"）、图标/组件规范、美学优化清单 |
| Phase 2 | 体验（ux） | 问题根因表（每条：现象→根因→修法）、对比度实测数字、动效规范（时长/属性/降级） |
| Phase 3 | 工程（engineer） | 按规范落地 + 自测证据 |
| 终审 | 主控（你自己） | **独立交叉验收**——不信任自测，亲手跑断言与截图 |

编排提示词要点（分派时写给每个 teammate）：
1. 明确交付物形态与验收标准（"交付 X，验收方式是 Y"）
2. **内容完整发给你**："把完整内容直接发我，我不会重读你的对话"——防 teammate 只发摘要
3. 禁止越界："只改授权范围，别动其他模块"
4. 要求自测证据："每项改动附验证方式与结果"

## 交叉验收纪律（主控）

- teammate 的"已验证"只代表其视角；关键结论（性能归因、跨浏览器行为、伪影判定）必须亲手复跑
- 自测与你的观察矛盾时（如"无横向滚动"但截图有裁切）：先打回定位根因，再亲自用探针裁定——两边都可能错，探针数据是唯一裁判
- 打回话术模板："发现 <现象>，与你的 <结论> 矛盾。请先定位根因（附复现方式），再修复；不要只加补丁。"
- 验收通过后才允许关闭：`TaskUpdate` 置完成 → 逐个 `shutdown_request` → 全部 `shutdown_response` 后删除团队

## 收尾交付清单结构（对用户的最终汇报）

1. **独立复核结论**：关键争议点的裁定 + 证据（探针数值）
2. **修复的问题**：表格式（编号/现象/根因/修法），含回归验证说明
3. **替换/重构项**：清单 + 统一规范描述
4. **新增/优化项**：按维度分组
5. **主动砍掉项**：每项附理由（帧预算/兼容缺陷/晕动症等）——砍要有名有姓，防止被当作遗漏
