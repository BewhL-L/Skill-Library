# 代码审查与重构实战手册（坏味道 · 原则 · 手法 · 评审清单）

> 供 code-review-refactor 评审与重构时参考。包含代码坏味道目录、SOLID 与设计原则、常用重构手法、五维评审清单、安全重构流程、模式选用、PR 协作与报告模板。语言以通用面向对象/主流栈为例，思想跨语言通用。

---

## 一、代码坏味道目录（先识别，再重构）

| 坏味道 | 典型信号 | 首选重构手法 |
|--------|---------|-------------|
| 长函数 Long Method | 一个函数超过一屏、注释分段、多重循环/分支 | 提取函数、以查询替代临时变量 |
| 重复代码 Duplication | 三处以上相似逻辑、复制粘贴改参数 | 提取函数/父类、模板方法、参数化 |
| 过大的类 Large Class | 字段/职责太多、一个类什么都管 | 提取类、拆职责 |
| 过长参数列表 Long Parameter List | 参数 ≥4、多个总是一起出现 | 引入参数对象、保持对象完整 |
| 深嵌套 Deep Nesting | if/for 嵌套 ≥3–4 层 | 卫语句提前返回、提取函数、多态 |
| 魔法数 Magic Number | 裸数字/裸字符串散落 | 具名常量/枚举 |
| 发散式变化/霰弹修改 | 一个改动要改很多处 / 一个类因不同原因改 | 按变化方向拆类、隔离变化 |
| 依恋情结 Feature Envy | 函数大量用别的类的数据 | 移动函数到它最关心的类 |
| 数据泥团 Data Clumps | 同一组数据到处一起出现 | 抽成值对象 |
| 基本类型偏执 Primitive Obsession | 用字符串/数字表达概念（金额、手机号、状态） | 值对象/枚举 |
| switch/if-else 类型码 | 按类型分支且会不断新增 | 以多态/策略替代条件 |
| 异常吞没 Swallowed Exception | catch 后空处理/只 print | 正确处理或抛出、带上下文 |
| 注释当解释 | 用注释解释写得差的代码 | 先重构让代码自解释，再保留"为什么"注释 |
| 僵尸代码/死代码 | 永不执行、被注释掉、无人调用 | 删除（靠版本控制保留历史） |
| 不当命名 | 名不副实、缩写难懂、a/b/tmp | 改名（最小但最高频的重构） |

> 经验顺序：**先命名、再函数粒度、再职责划分、最后才是模式**。80% 的可维护性问题靠"改名 + 提取函数"就能解决。

## 二、设计原则速查（坏味道的根因层）

### SOLID
| 原则 | 含义 | 违反信号 |
|------|------|---------|
| 单一职责 SRP | 一个类/函数只有一个变化原因 | 一个类里混了业务逻辑、持久化、格式化 |
| 开闭 OCP | 对扩展开放、对修改关闭 | 每加一种类型都要改同一处 switch |
| 里氏替换 LSP | 子类能替换父类且行为不破坏契约 | 子类抛不支持异常、弱化前置/强化后置 |
| 接口隔离 ISP | 客户不依赖它不用的方法 | 胖接口逼实现类写空方法 |
| 依赖倒置 DIP | 依赖抽象而非具体实现 | 高层直接 new 低层实现、难以替换/测试 |

### 配套原则
- **DRY**：知识/逻辑单一出处（注意：偶然相似不算重复，别为复用硬耦合）
- **KISS / YAGNI**：选最简单可行方案；不为"将来可能需要"提前抽象
- **三次法则**：第一次直接写、第二次相似先忍着、第三次重复才抽象
- **组合优于继承**：优先组合获得灵活性，仅在真正"is-a"且契约稳定时继承
- **命令查询分离 CQS**、**失败快速 fail-fast**、**显式优于隐式**

## 三、常用重构手法（小步、行为不变）

| 手法 | 怎么做 | 解决的坏味道 |
|------|--------|-------------|
| 改名 Rename | 改函数/变量/类名以达意，借助 IDE 一次到位 | 不当命名 |
| 提取函数 Extract Method | 把一段代码抽成命名清晰的函数 | 长函数、深嵌套、注释分段 |
| 内联函数 Inline Method | 函数体比名字还简单时合回去 | 过度间接 |
| 以查询替代临时变量 | 把计算表达式抽成具名查询 | 临时变量泛滥 |
| 卫语句替换嵌套 | 不满足条件提前 return，去掉 else 层级 | 深嵌套 |
| 引入参数对象/值对象 | 把成组参数/基本类型封装成对象 | 长参数、数据泥团、基本类型偏执 |
| 移动函数/字段 | 放到数据/职责真正所属的类 | 依恋情结、职责错位 |
| 提取类 | 把一组相关字段和方法拆成新类 | 过大类、发散变化 |
| 以多态/策略替代条件 | 每类型一个实现，公共处只调抽象 | switch 类型码、违反 OCP |
| 以组合替代条件/循环 | 用集合操作（map/filter/reduce）替代命令式循环 | 冗长循环逻辑 |
| 移动边界/收口参数 | 在边界校验、内部使用可信值 | 重复校验、非法状态扩散 |

> 每次只做一种手法 → 跑测试 → commit。IDE 的安全重构（Rename/Extract/Move）优先于手改。

## 四、五维评审清单（结构化 Review 用）

### 4.1 正确性与边界（P0 为主）
- 空值/空集合/单元素/超长/最大值是否处理
- 边界条件（off-by-one）、并发（竞态、死锁、可见性）、事务边界
- 异常路径：是否吞没、错误信息是否足够定位、失败后状态是否一致
- 资源：连接/流/文件是否正确关闭，有无泄漏
- 逻辑是否真的实现需求，幂等性、重试与重复提交

### 4.2 安全（P0）
- 注入：SQL 是否参数化、命令/模板是否拼接用户输入、XSS
- 鉴权与越权：身份校验、水平/垂直越权（能否操作他人数据）
- 敏感信息：密钥是否硬编码、是否落日志/返回前端、传输是否加密
- 输入校验与输出编码、不安全反序列化、SSRF/路径遍历
- 依赖是否有已知漏洞、是否最小权限

### 4.3 性能（P1，先证据后优化）
- N+1 查询、循环内 IO/远程调用、缺索引/全表扫描
- 不必要的对象创建、大对象全量加载、缓存策略与失效
- 锁粒度、阻塞调用、同步异步选择、分页
- 要求：用 profiling/慢查询/压测量化，避免"感觉慢"的过早优化

### 4.4 可维护性（P1/P2）
- 对照第一节坏味道目录逐项扫
- 命名是否达意、函数/类职责是否单一、模块耦合方向
- 是否符合 SOLID/DRY/KISS；有无过度设计
- 注释解释"为什么"而非"做什么"；是否有死代码

### 4.5 测试（P1）
- 核心逻辑是否有单测；正常/边界/异常三类是否齐全
- 断言是否有效（不是只断言"不抛异常"）
- 是否可测（依赖能否注入/Mock）、测试是否稳定独立
- 关键路径有无集成测试；测试命名是否表达意图

## 五、安全重构流程（保证行为不变）

```
1. 建安全网
   - 已有可靠测试 → 直接用
   - 没测试 → 先写"特征测试(Characterization Test)"记录当前真实行为
2. 明确目标：列出要消除的坏味道与目标结构，不在重构中加需求/改行为
3. 拆成最小步：每步只用一种重构手法（优先 IDE 安全重构）
4. 每步验证：改一点就跑全部相关测试，必须全绿；红了立刻回退到上一绿
5. 频繁提交：一个绿状态一个 commit（message 标 refactor:，与 feat/fix 分开）
6. 行为不变核对：重构前后跑同一测试/对比关键输出；确需改行为，另起步骤与提交
7. 收尾：删除死代码、补上新结构应有的测试、跑 lint/类型检查/全量回归
```

> 黄金法则：**重构（refactor）与修 bug、加功能严格分开提交**。混在一起，出问题无法定位是"改坏了"还是"新逻辑错了"。

## 六、设计模式：何时用、何时别用

| 需求/坏味道 | 可考虑模式 | 不要用的信号 |
|-------------|-----------|-------------|
| 多种算法/类型运行时切换 | Strategy | 只有两种且不会变，if 更简单 |
| 按类型不断加分支（违反 OCP） | Polymorphism / State | 类型集合封闭不变 |
| 创建过程复杂、要解耦 | Factory | new 一个对象就够时 |
| 需要跨多步骤构建复杂对象 | Builder | 参数很少时 |
| 一对多通知、事件解耦 | Observer/Pub-Sub | 只有一个固定接收方 |
| 给对象动态叠加能力 | Decorator | 组合爆炸但层级固定可用配置 |
| 统一封装复杂子系统 | Facade | 只是为了"显得有设计" |
| 算法骨架固定、子步骤可变 | Template Method | 步骤并不稳定 |

原则：**模式是被变化点"逼"出来的，不是先验套上去的**。引入前回答：不引入会怎样？变化真的会发生吗？团队能看懂吗？

## 七、PR Code Review 协作规范

### 7.1 评审顺序
1. 先看**设计与接口**：方向对不对、职责划分、公共 API 是否合理（方向错了抠细节无意义）
2. 再看**主流程与正确性/安全**（P0/P1）
3. 最后看**可读性、风格、测试**（P2/nit）
4. 超大 PR（>400 行）建议请作者拆分，评审质量随体积骤降

### 7.2 评论分级与措辞
- `[P0]` 必须改：bug、安全、数据风险
- `[P1]` 建议本次改：设计、性能、缺测试
- `[P2]/nit:` 可选：风格、命名、小优化
- 对事不对人：评"这段在 X 情况下会 NPE"，不评"你怎么又没判空"
- 用提问引导："这里如果并发调用会不会有问题？"；给替代方案而非只否定
- 看到亮点明确肯定，评审是双向成长

### 7.3 接收评审
- 先复述确认理解，不急于辩解；有分歧用数据、最小示例、官方文档讨论
- 每条意见三选一闭环：**接受并修改 / 解释后保留 / 另开 issue 跟踪**，不无下文
- 作者对结果负责，不因为"是 reviewer 让我改的"就放弃自己的判断

```markdown

**总体评价**：2-4 句（设计是否合理、最大亮点、最主要问题）

### P0 阻断项（必须改）
1. 【位置 file::func】问题：… ｜ 原因：… ｜ 建议：…（给最小改法）
### P1 重要（建议本次改）
…
### P2 / nit（可选）
…

### 坏味道与设计
- 识别到的坏味道 → 对应原则 → 建议手法

### 重构建议（如需要）
- 测试安全网现状：有/需补特征测试
- 小步计划：① … ② … ③ …（每步可独立提交、测试全绿）
- 行为不变如何验证：…

### 测试建议
- 需补：正常/边界/异常用例清单
```

## 九、一个端到端迷你示例（思想演示）

**坏味道**：一个下单函数里嵌套 3 层、裸数字、混了优惠计算、库存、日志。
1. 建测试：先补"给定商品与用户→订单金额/库存结果"的特征测试锁住行为
2. 改名 + 提取函数：抽出 `calcDiscount()`、`deductStock()`、`buildOrderLog()`，主函数只剩编排
3. 魔法数改具名常量（`VIP_DISCOUNT_RATE`），优惠规则若会频繁变化再用 Strategy（否则停在第 2 步，YAGNI）
4. 每抽一个函数跑一次测试并 `refactor: extract ...` 提交
5. 补边界用例（空购物车、库存不足、折扣后为负），全量回归绿
6. 结果：主流程一眼可读、每块可独立测试、新增优惠类型只改一处——但没有为不存在的变化过度抽象

> 重构的目标不是"用了多少模式"，而是**同样的行为、更清晰的意图、更低的修改成本**。
