# 技术选型决策框架

> 本文件定义软件类项目的技术选型决策流程。AI 不得随意选择框架，必须按本框架四步推导，并在指导文档中说明选型理由。

---

## 核心原则

1. **需求驱动**：技术选型必须从项目需求出发，不是从"我熟悉什么"出发
2. **约束优先**：先考虑硬约束（时间/预算/人力/环境），再考虑技术偏好
3. **对比决策**：至少对比 2-3 个候选方案，说明为什么选这个而不是那个
4. **可解释性**：选型理由必须写进指导文档，用户能理解为什么这么选
5. **求职导向**：如果用户是为了找工作，优先选市场需求大、面试常考的技术栈

---

## 四步决策流程

### 第一步：明确需求与约束

列出以下信息，作为选型的输入：

| 维度 | 具体内容 | 示例 |
|------|---------|------|
| 项目目标 | 做完要达到什么效果 | "可上线的微信小程序" |
| 核心功能 | 必须实现的功能列表 | "用户注册/发布/关注/私信" |
| 性能要求 | 并发量/响应时间/数据量 | "支持 1000 并发，响应 < 500ms" |
| 时间约束 | 交付期限 | "2 周内完成 MVP" |
| 预算约束 | 服务器/服务/工具费用 | "每月云服务 < 100 元" |
| 人力约束 | 几个人开发/什么水平 | "1 人全栈，初学者" |
| 环境约束 | 部署环境/操作系统/网络 | "部署到国内云服务器" |
| 用户目标 | 求职/学习/商用/个人用 | "为了找工作，需要简历亮点" |

### 第二步：确定候选方案

根据需求和约束，列出 2-3 个可行的候选方案。每个方案包含：

- 前端框架/技术
- 后端框架/语言
- 数据库
- 部署方案
- 核心依赖库

**候选方案来源**：
- 市场主流方案（招聘需求最多的）
- 项目类型常用方案（社交类用什么、电商类用什么）
- 用户已有基础（用户学过什么、用过什么）
- 时间/预算约束下的最简方案

### 第三步：多维度对比评估

对每个候选方案，按以下维度打分（1-5 分），加权计算总分：

| 维度 | 权重 | 评估标准 |
|------|------|---------|
| 需求匹配度 | 25% | 能否满足核心功能和性能要求 |
| 学习成本 | 20% | 用户当前水平能否快速上手（初学者优先选文档多、社区大的） |
| 开发效率 | 15% | 开发速度、生态完善度、脚手架支持 |
| 部署运维 | 15% | 部署难度、运维成本、云服务支持 |
| 市场需求 | 15% | 招聘需求量、面试频率（求职项目权重提高到 25%） |
| 扩展性 | 10% | 未来功能扩展、性能扩展的难易度 |

**对比表示例**：

| 维度 | 权重 | 方案A（FastAPI+小程序） | 方案B（Node+React） | 方案C（Java+Vue） |
|------|------|------------------------|---------------------|-------------------|
| 需求匹配度 | 25% | 5 | 4 | 5 |
| 学习成本 | 20% | 4 | 3 | 2 |
| 开发效率 | 15% | 5 | 4 | 3 |
| 部署运维 | 15% | 4 | 4 | 3 |
| 市场需求 | 15% | 3 | 5 | 5 |
| 扩展性 | 10% | 4 | 5 | 5 |
| **加权总分** | | **4.35** | **4.10** | **3.85** |

### 第四步：最终选型与理由说明

选择总分最高的方案，并在指导文档中写明：

1. **最终选型**：明确列出技术栈清单
2. **选型理由**：
   - 为什么选这个（对应需求和约束的匹配点）
   - 为什么不选其他候选（对比中的劣势）
3. **风险与应对**：
   - 选型可能带来的风险（如某框架社区不够活跃）
   - 应对措施（如预留切换接口、选择成熟版本）
4. **学习路径**：
   - 用户需要先学什么、再学什么
   - 每个技术的学习重点

## 常见项目类型的推荐技术栈

> 以下为参考，具体项目仍需按四步流程决策。

### 社交/内容平台（求职向）

| 层级 | 推荐方案 | 理由 |
|------|---------|------|
| 前端 | 微信小程序 / React Native | 小程序求职需求大，RN 跨平台 |
| 后端 | FastAPI (Python) / Spring Boot (Java) | FastAPI 开发快，Spring Boot 市场需求最大 |
| 数据库 | PostgreSQL / MySQL | 关系型数据库，社交数据关系复杂 |
| 缓存 | Redis | 热点数据缓存、会话管理 |
| 实时通信 | WebSocket | 私信/通知实时推送 |
| 搜索 | Elasticsearch（进阶） | 全文搜索，初级可用 SQL LIKE |

### 电商平台

| 层级 | 推荐方案 | 理由 |
|------|---------|------|
| 前端 | Vue3 + TypeScript / 微信小程序 | Vue 国内需求大，小程序适合电商 |
| 后端 | Spring Boot (Java) / NestJS (Node) | Java 电商生态最成熟 |
| 数据库 | MySQL + Redis | 电商标准组合 |
| 搜索 | Elasticsearch | 商品搜索必备 |
| 消息队列 | RabbitMQ / Kafka | 订单异步处理 |

### 工具/效率应用

| 层级 | 推荐方案 | 理由 |
|------|---------|------|
| 前端 | React / Vue3 | 组件化开发，工具类应用交互复杂 |
| 后端 | FastAPI / Express | 轻量快速，工具类应用后端简单 |
| 数据库 | SQLite（开发）/ PostgreSQL（生产） | 工具类应用数据量小 |
| 部署 | Vercel / Railway | 一键部署，成本低 |

### 学习/成长项目（非代码）

| 类型 | 推荐工具 | 理由 |
|------|---------|------|
| 知识管理 | Obsidian / Notion | 双链笔记，适合知识体系 |
| 任务管理 | Todoist / 飞书任务 | 跨平台，提醒功能强 |
| 时间记录 | Toggl / 番茄ToDo | 数据统计完善 |
| 笔记发布 | 语雀 / 微信公众号 | 国内访问好 |

## 选型反模式（禁止）

1. **追新不追稳**：选刚发布的框架/版本，社区不成熟、文档不全、坑多
   - ✅ 正确：选稳定版本（如 React 18 而非最新 RC 版）
2. **过度设计**：小项目用微服务/K8s，增加不必要的复杂度
   - ✅ 正确：小项目用单体架构，够用就好
3. **技术堆砌**：为了"简历好看"堆 10 种技术，实际只用 2 种
   - ✅ 正确：每种技术都有明确的使用场景，不堆砌
4. **忽视用户基础**：给初学者选 Rust/Go 等学习曲线陡峭的语言
   - ✅ 正确：根据用户水平选，初学者优先 Python/JS 等生态成熟的语言
5. **不说明理由**：直接列技术栈，不解释为什么这么选
   - ✅ 正确：按四步流程推导，写明选型理由

## 输出模板

在指导文档中，技术选型部分应包含：

```markdown
## 技术选型

### 选型过程
1. 需求与约束：（列出第一步的结果）
2. 候选方案：（列出 2-3 个方案）
3. 对比评估：（对比表 + 加权总分）
4. 最终选型：（明确技术栈）

### 技术栈清单
| 层级 | 技术 | 版本 | 用途 |
|------|------|------|------|
| 前端 | XXX | X.X | XXX |
| 后端 | XXX | X.X | XXX |
| 数据库 | XXX | X.X | XXX |
| ... | ... | ... | ... |

### 选型理由
- 为什么选这个：...
- 为什么不选其他：...

### 风险与应对
- 风险 1：... → 应对：...
```

---

*技术选型不是一次性决策，项目迭代过程中如果发现选型不合适，可以按本框架重新评估并切换。*
