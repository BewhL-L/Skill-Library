## 二、项目难度递进标准

### 四级难度体系

| 难度 | 标识 | 技能要求 | 项目复杂度 | 预计时间 | 典型项目 |
|------|------|---------|-----------|---------|---------|
| 入门 | 🟢 | 掌握基础语法，能照着写 | 单文件/简单CRUD，1-2个技术点 | 1-2天 | Streamlit数据分析仪表盘、简单Todo应用 |
| 进阶 | 🟡 | 掌握框架核心用法，理解基本原理 | 前后端分离，3-5个模块，完整CRUD+权限 | 3-5天 | FastAPI+Vue3后台管理系统、RAG知识库问答、爬虫+可视化平台 |
| 高级 | 🔴 | 深入理解原理，能做架构设计 | 微服务/分布式，5+模块，高并发/性能优化 | 1-2周 | SpringCloud微服务电商、AI Agent平台、企业级RAG、多模态生成平台 |
| 专家 | ⚫ | 源码级理解，能做技术决策 | 复杂系统设计，跨语言/跨领域，架构演进 | 2-4周 | 统一AI网关、多语言混合架构、实时协作系统、云原生架构 |

### 项目能力递进路径

```
入门级：单文件应用 → 简单CRUD → 理解Web应用基本结构
    ↓
进阶级：前后端分离 → 权限+缓存 → AI功能集成 → 掌握全栈开发流程
    ↓
高级：微服务架构 → 分布式事务 → 高并发优化 → 掌握分布式系统设计
    ↓
专家级：复杂系统设计 → 架构决策 → 技术领导力 → 掌握体系化架构能力
```

### 按学习阶段推荐项目

| 学习阶段 | 推荐项目类型 | 技能目标 |
|---------|------------|---------|
| 🌱 入门筑基 | 入门级单文件应用 | 理解Web应用基本结构、掌握基础语法 |
| ⚡ 进阶实战 | 进阶级全栈项目 + AI项目 | 掌握全栈开发流程、掌握AI应用开发 |
| 🏗️ 高级架构 | 高级微服务项目 + 架构案例 | 掌握微服务架构、掌握分布式系统设计 |
| 👑 专家精通 | 专家级复杂系统 + 架构演进 | 掌握复杂系统设计、培养技术领导力 |

## 三、项目代码组织规范

### 按文件组织代码

**原则**：每个代码块对应一个真实文件，文件名写在代码块顶部注释中。

```python
# config.py
from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    # 配置内容
    ...

settings = Settings()
```

**禁止**：
- ❌ 把多个文件的代码混在一个代码块中
- ❌ 代码块不标注文件名
- ❌ 只给代码片段，不给完整可运行文件

### 项目结构树规范

**位置**：步骤1（项目初始化）之后，展示完整项目结构。

**格式**：
```
项目名称/
├── main.py              # 入口文件说明
├── config.py            # 配置管理
├── core/                # 核心模块目录
│   ├── __init__.py
│   ├── module1.py       # 模块1说明
│   └── module2.py       # 模块2说明
├── api/                 # API层
│   └── routes.py
├── models/              # 数据模型
├── services/            # 业务逻辑
├── tests/               # 测试
├── requirements.txt     # 依赖
├── .env.example         # 环境变量示例
└── README.md            # 项目说明
```

**规范**：
- 每个文件/目录后用 `#` 注释说明作用
- 目录用 `/` 结尾
- 层级用 `├──`、`└──`、`│` 表示
- 按重要性排序，核心文件在前

### 代码质量要求

| 要求 | 说明 |
|------|------|
| 可运行 | 所有代码块组合起来能直接运行，不缺关键部分 |
| 有注释 | 关键逻辑有注释，复杂算法有思路说明 |
| 错误处理 | 有基本的异常捕获和错误提示 |
| 配置分离 | 配置项不硬编码，用配置文件或环境变量 |
| 命名规范 | 变量/函数/类名符合对应语言的命名规范 |
| 安全 | 不硬编码密钥、密码，用环境变量 |

## 四、项目验收标准模板

### 验收标准编写原则

1. **可量化**：每条标准都能明确判断是否达成，不用模糊词
2. **可验证**：每条标准都有明确的验证方法
3. **覆盖核心功能**：至少覆盖项目的 5 个核心功能点
4. **分层级**：基础功能必须达标，进阶功能可选

### 标准格式

```
> 🎯 **项目验收标准**：
> ① {{功能1}}：{{可量化的验收条件，如"能上传PDF并自动索引"}}
> ② {{功能2}}：{{可量化的验收条件，如"提问后能基于文档准确回答"}}
> ③ {{功能3}}：{{可量化的验收条件，如"回答流式输出，首字延迟<2秒"}}
> ④ {{功能4}}：{{可量化的验收条件，如"回答中注明来源文档"}}
> ⑤ {{功能5}}：{{可量化的验收条件，如"支持至少3种文档格式（PDF/MD/TXT）"}}
```

### 各类型项目验收标准参考

**全栈项目**：
- ① 用户注册登录，JWT认证
- ② 完整CRUD（增删改查）
- ③ 权限管理（至少2种角色）
- ④ 文件上传下载
- ⑤ 前端页面完整，响应式布局

**AI项目**：
- ① 核心AI功能可用（如问答/生成/对话）
- ② 流式输出（如适用）
- ③ 上下文记忆（如适用）
- ④ 支持至少1种输入格式
- ⑤ 有基本的错误处理（如API调用失败）

**架构案例**：
- ① 架构图完整，各模块职责清晰
- ② 核心流程有时序图
- ③ 关键技术有选型对比和理由
- ④ 有性能/容量估算
- ⑤ 有高可用/扩展性设计

## 五、项目 MOC 结构规范

### 项目 MOC 标准结构

```
1. Frontmatter（title/tags/category/created/updated/hub:true）
2. 内容地图说明（涵盖领域、文档数、核心理念）
3. 项目分类总览（Mermaid mindmap）
4. 五大分类（每类有项目表格：项目/技术栈/难度/核心技能）
5. 项目学习顺序（Mermaid flowchart）
6. 按阶段推荐项目表格（学习阶段/推荐项目/技能目标）
7. 项目能力递进（Mermaid flowchart，四级递进）
8. 跨领域关联表格（关联领域/关联点/对应笔记）
9. 标签体系
10. 底部导航
```

### 项目表格规范

| 列名 | 说明 | 示例 |
|------|------|------|
| 项目 | 双链链接到项目文档 | `[[实战-FastAPI+RAG知识库问答]]` |
| 技术栈 | 核心技术，用 + 连接 | `FastAPI + LangChain + Chroma + Vue3` |
| 难度 | 🟢入门 / 🟡进阶 / 🔴高级 | 🟡进阶 |
| 核心技能 | 3-5个关键技能点 | `RAG全流程、向量检索、流式输出` |

## 六、项目文档编写最佳实践

### 1. 实操步骤编写规范

| 要素 | 要求 |
|------|------|
| 步骤数 | 6-10步，覆盖从初始化到运行的完整流程 |
| 每步内容 | 步骤标题 + 说明 + 完整代码块 |
| 代码完整性 | 每个代码块是完整可运行的文件，不是片段 |
| 递进性 | 步骤之间有逻辑递进，前一步是后一步的基础 |
| 可验证 | 每步完成后有可验证的结果（如运行命令、访问页面） |

### 2. 常见问题模块规范

- 至少 4-6 个常见问题
- 表格格式：问题 / 原因 / 解决方案
- 问题要真实，是开发中实际会遇到的
- 解决方案要具体，可操作
- 附加性能优化建议（3-4条）

### 3. 进阶与最佳实践模块规范

- 生产环境增强（4-5个进阶方向）
- 每个方向有简要说明
- 部署方案（Dockerfile 或部署步骤）
- 关联到知识库中的进阶笔记

### 4. 关联笔记规范

- 至少 5-7 个关联笔记
- 覆盖项目涉及的核心技术点
- 用 `·` 分隔，紧凑排列
- 关联笔记应该是知识库中真实存在的文档
