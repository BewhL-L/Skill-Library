# 调试指南

> 本文档描述 career-life-guidance Skill 常见问题的排查和解决方法。

## 常见问题排查

### 1. 生成的手册内容空泛、不具体

**症状**：手册充满宏观分析和正确的废话，缺少具体可执行的动作。

**排查步骤**：
1. 检查是否完成了身份校准（8个字段是否锁定）
   - 身份不清晰 → 内容必然空泛
   - 解决：回到第1步，主动询问缺失的身份字段

2. 检查是否遵循了"每个建议包含三要素"
   - 为什么重要
   - 具体怎么做（步骤、工具、资源）
   - 不做的后果
   - 缺少任何一个要素 → 建议就会空泛

3. 检查密度指标
   - 每1000字是否至少1个可执行动作
   - 每章是否至少1张表格或流程图
   - 不达标 → 需要补充具体内容

4. 检查是否引用了参考文档
   - 学习路线是否参考了 `references/04-learning-roadmap.md`
   - 项目实战是否参考了 `references/05-project-playbook.md`
   - 未参考 → 内容容易流于表面

**常见原因**：
- 身份校准不完整，用通用内容代替个性化内容
- 跳过了参考文档，凭印象写作
- 追求字数而忽略密度，用宏观分析填充篇幅
- 项目篇篇幅不足（应占25%-35%）

---

### 2. 项目实战部分不够深入

**症状**：项目只有标题和简单描述，缺少完整的实现指南。

**排查步骤**：
1. 检查项目数量
   - 是否至少3个从易到难的项目
   - 少于3个 → 需要补充

2. 检查每个项目的完整度
   - 每个项目是否包含：需求分析→技术选型→实现指南→工程化→部署→简历包装
   - 缺少任何环节 → 项目不够深入

3. 检查项目篇篇幅
   - 是否占全书25%-35%
   - 不足 → 需要大幅扩充

4. 检查是否参考了 `references/05-project-playbook.md`
   - 该文档包含完整的项目设计模板和实现指南
   - 未参考 → 项目容易停留在表面

**解决方法**：
- 按照 `references/05-project-playbook.md` 的项目模板重新设计
- 每个项目至少包含：项目背景、功能清单、技术栈、架构图、核心模块实现代码、测试方案、部署步骤、简历描述模板
- 入门级项目：1-2周可完成，验证基础能力
- 进阶级项目：3-4周可完成，展示工程能力
- 高级级项目：5-8周可完成，体现深度和创新

---

### 3. 身份校准不充分，内容不贴合用户

**症状**：手册内容看起来适用于任何人，但没有针对用户的具体情况。

**排查步骤**：
1. 检查8个身份字段是否全部锁定
   - 学历背景、当前阶段、工作经验、年龄、所在城市、目标设定、约束条件、偏好倾向
   - 任何一个字段缺失 → 内容就会缺乏针对性

2. 检查是否主动询问了缺失信息
   - 用户输入模糊时，是否主动追问
   - 还是直接用默认值猜测

3. 检查内容中是否体现了用户身份
   - 学习计划是否考虑了用户的可投入时间
   - 项目选择是否匹配用户的基础和目标
   - 求职策略是否针对用户的经验水平
   - 城市选择是否考虑了用户所在城市的就业市场
   - 薪资目标是否合理（基于用户背景和城市行情）

**解决方法**：
- 严格按照 `references/01-user-profiling.md` 的8个字段进行校准
- 字段不完整时主动询问，不猜测
- 每个章节的内容都要回扣用户身份，问自己"这个建议对这个人具体意味着什么"
- 避免使用"你应该..."的通用句式，改用"考虑到你是[身份]，建议你..."的个性化句式

### 4. 六篇结构不完整或比例失调

**症状**：某些篇章缺失，或者篇幅比例严重失调（如学习篇占60%，项目篇只占10%）。

**排查步骤**：
1. 检查六篇是否齐全
   - 第一篇：决策与方向
   - 第二篇：学习与成长
   - 第三篇：项目与实战
   - 第四篇：求职与入职
   - 第五篇：站稳与发展
   - 第六篇：支撑与风险
   - 任何一篇缺失 → 结构不完整

2. 检查篇幅比例
   - 决策篇：10%-15%
   - 学习篇：15%-20%
   - 项目篇：25%-35%（重中之重）
   - 求职篇：15%-20%
   - 发展篇：10%-15%
   - 支撑篇：10%-15%
   - 严重偏离 → 需要调整

3. 检查固定套件是否齐全
   - 写在前面（致读者的信 + 使用指南）
   - 能力总览（全书能力地图 + 优先级矩阵）
   - 篇小结（每篇结束后的行动清单 + 检查点）
   - 收尾套件（资源清单、工具推荐、书单、模板、FAQ）
   - 文档信息（版本、更新日志、使用说明、免责声明）

**解决方法**：
- 使用 `assets/document-template.md` 作为骨架，确保六篇结构完整
- 参考 `references/03-six-phase-structure.md` 和 `references/12-document-anatomy.md` 的篇幅分配标准
- 项目篇必须是重中之重，占25%-35%篇幅
- 每篇结束后必须有篇小结（行动清单 + 检查点）

### 5. 写作风格不符合"前辈语气"

**症状**：手册读起来像教科书或行业报告，冷冰冰的，没有温度。

**排查步骤**：
1. 检查是否使用了说教式语气
   - "你必须..."、"你应该..."、"千万不要..."
   - 这种语气会让读者感到被指责

2. 检查是否有个人化表达
   - 是否有"我见过很多人..."、"以我的经验..."、"我建议你..."
   - 缺少个人化表达 → 像AI生成的通用内容

3. 检查是否有具体的故事和案例
   - 是否有真实的人物故事（可以是化名）
   - 是否有具体的失败案例和教训
   - 缺少故事 → 内容缺乏说服力和温度

4. 检查是否参考了 `references/09-writing-style.md`
   - 该文档包含完整的"前辈语气"配方
   - 未参考 → 风格容易跑偏

**前辈语气配方**：
- 像一个走过这条路的前辈，坐在对面跟你说实在话
- 有温度但不鸡汤，有建议但不说教
- 承认困难，但给出出路
- 用"我见过..."、"以我的经验..."、"我建议你..."代替"你必须..."
- 每个建议都有具体的操作步骤，不是空泛的鼓励
- 适当使用反问和设问，引导读者思考

### 6. 多轮迭代没有深化，只是重复

**症状**：第2版、第3版和第1版内容差不多，只是字数增加了，没有实质深化。

**排查步骤**：
1. 检查每轮迭代的深化方向是否明确
   - 第1版：骨架完整 + 核心内容
   - 第2版：项目实战深化
   - 第3版：求职细节 + 支撑维度
   - 第4版：长期发展 + 风险预案
   - 第5版：整体润色 + 密度提升
   - 方向不明确 → 迭代就会盲目

2. 检查每轮是否有明确的验收标准
   - 第2版验收：项目篇达到25%-35%篇幅，每个项目有完整实现指南
   - 第3版验收：求职篇包含简历模板/面试题库，7大支撑维度齐全
   - 没有验收标准 → 无法判断迭代是否达标

3. 检查是否参考了 `references/11-iteration-protocol.md`
   - 该文档包含完整的迭代协议
   - 未参考 → 迭代容易失控

**解决方法**：
- 严格按照 `references/11-iteration-protocol.md` 的迭代流程执行
- 每轮迭代前明确深化方向和验收标准
- 每轮迭代后按验收标准检查，不达标不进入下一轮
- 避免在一轮迭代中试图完成所有深化，聚焦一个方向做深做透

---

### 7. 输出格式不符合Obsidian标准

**症状**：双链格式错误、Frontmatter缺失、流程图无法渲染。

**排查步骤**：
1. 检查双链格式
   - 正确：`[[文档名]]` 或 `[[文档名|显示文字]]`
   - 错误：`[文档名](url)`、`【文档名】`

2. 检查Frontmatter
   - 是否在文档开头有YAML Frontmatter
   - 包含：title、date、tags、version、author等字段

3. 检查流程图格式
   - 是否使用了Mermaid语法
   - 是否用```mermaid代码块包裹
   - 语法是否正确（可在Obsidian中预览验证）

4. 检查是否参考了 `references/10-obsidian-output.md`
   - 该文档包含完整的Obsidian输出规范

**解决方法**：
- 严格按照 `references/10-obsidian-output.md` 的格式标准输出
- 输出前在Obsidian中预览，确保双链、流程图、Frontmatter正常渲染
- 使用标准的Markdown语法，避免使用非标准扩展

## 质量问题排查

### 内容密度不足

**症状**：字数很多，但可执行的动作很少，大部分是宏观分析和正确的废话。

**检查方法**：
- 统计每1000字中的可执行动作数量（目标：≥1个）
- 统计每章的表格和流程图数量（目标：≥1个）
- 检查每个建议是否包含"为什么+怎么做+不做后果"三要素

**解决方法**：
- 删除空泛的宏观分析，替换为具体的操作步骤
- 每个建议都补充具体的工具、资源、时间、步骤
- 多用表格和流程图，少用大段文字
- 项目篇必须做深做透，这是全书密度最高的部分

### 个性化不足

**症状**：手册内容看起来对任何人都适用，但没有针对用户的具体情况。

**检查方法**：
- 检查8个身份字段是否全部体现在内容中
- 学习计划是否考虑了用户的可投入时间
- 项目选择是否匹配用户的基础和目标
- 求职策略是否针对用户的经验水平
- 城市选择是否考虑了用户所在城市

**解决方法**：
- 每个章节的内容都要回扣用户身份
- 避免通用句式，使用个性化句式
- 用用户的具体情况举例，而不是用抽象的"某人"
- 薪资、时间、城市等数据要基于用户的实际情况
