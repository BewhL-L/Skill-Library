# code-review-refactor 常见问题解答

> 使用代码审查与重构教练时的常见问题和解答。

---

## Q1：这段代码能跑、需求也对，还有必要重构吗？

**A**：看"修改成本"而非"能不能跑"。能跑但每次改需求都提心吊胆、牵一发动全身，就值得重构；判断信号：
1. 同类 bug 反复出现、改一个地方要动很多文件（坏味道：霰弹修改）
2. 函数过长/嵌套过深，自己过两周都读不懂
3. 无法给它写测试，或测试要 mock 一大堆东西（耦合过重）
4. 新增一种类型就得改同一处大 switch（违反开闭原则）

反过来，**稳定、很少改动、已经测好的代码**，哪怕不那么优雅也别急着动——重构服务于"未来还要改"，不为洁癖服务。优先重构"即将被修改/正在出问题"的部分（童子军军规：离开时让它比来时干净一点）。

---

## Q2：没有单元测试，能直接重构吗？

**A**：不能裸改，但可以先补"安全网"再重构：
1. **特征测试（Characterization Test）**：先不评判对错，用测试把代码**当前真实行为**记录下来（给定输入→实际输出），哪怕行为有怪癖也先锁住
2. 有了这张网，再小步重构，每步都用它确认"行为没变"
3. 重构完成、结构清晰后，再补真正的边界/异常测试，并决定是否修正原先锁定的"怪行为"（改行为要单独提交）
4. 纯展示/脚本类一次性代码可降低要求，核心业务逻辑必须有网

记住：**没有测试的重构 = 赌博**。测试不是重构之后的事，而是重构的前提。

---

## Q3：重构和重写（rewrite）有什么区别？什么时候才该重写？

**A**：
- **重构**：在**外部行为不变**的前提下，小步调整内部结构，每步可运行、可回退、随时能停下来交付——默认首选
- **重写**：推倒重来，周期长、风险高、期间旧代码还要继续修 bug，容易陷入"永远重写不完"的泥潭

只有当：技术栈被淘汰、架构从根上无法支撑需求、维护成本已高于重写成本，且有充足资源与灰度方案时，才考虑重写；即便重写，也尽量用"绞杀者模式"逐模块替换，而不是停掉业务另起炉灶。绝大多数"想重写"的冲动，用分阶段重构就能解决。

## Q4：设计原则和模式那么多，我怎么知道该用哪个？是不是用得越多越高级？

**A**：恰恰相反，模式是被"真实变化点"逼出来的，不是越多越好。决策顺序：
1. 先保证清晰命名 + 合理函数粒度（解决 80% 问题）
2. 再按 SOLID 调整职责与依赖方向
3. **只有当某处确实反复变化/扩展痛苦时**，才引入对应模式（见 playbook 的"模式何时用"表）
4. 引入前先问：不引入会怎样？这个变化真会发生吗？团队看得懂吗？（YAGNI/KISS）

判断坏味道→反推被违反的原则→选最小的手法，而不是"我刚学了策略模式，看哪都像策略模式"。过度设计比轻微重复更难维护。

## Q5：给同事做 Code Review，怎么提意见不伤和气又能解决问题？

**A**：对事不对人、分级、可执行：
1. 评代码不评人：说"这里在并发下可能超卖"，不说"你怎么又没加锁"
2. 标级别：`[P0]` 必须改（bug/安全）、`[P1]` 建议改、`nit:` 小风格，让对方知道轻重
3. 每条意见给**理由和替代写法**，不用"优化下""不优雅"这类无法执行的话
4. 多用提问引导思考："这个分支如果 list 为空会怎样？"
5. 先肯定做得好的，再谈问题；拿不准就说"我可能没看懂，这里是考虑…吗？"
6. 风格类问题交给 lint/格式化工具统一，不在 PR 里争个人偏好

目标是"一起让代码更好"，不是证明谁高明。

## Q6：AI 生成的代码，怎么做 Review 才放心？

**A**：默认"未经证实"，按比人写的代码更严的标准过（联动 `ai-assisted-coding`）：
1. **正确性与边界**：AI 最容易写出"看着对但漏空值/并发/异常"的代码，重点构造边界用例
2. **安全红线**：注入、鉴权越权、硬编码密钥、外部输入校验，逐行人工看
3. **幻觉排查**：是否调用了项目里/该版本里根本不存在的 API、依赖，实际跑一遍
4. **过度设计**：AI 常为简单需求引入多余抽象/依赖，按 YAGNI 砍掉
5. 让 AI 自陈"最可能出问题的 3 个点"，再独立验证；可换一个模型交叉评审
6. 最终标准不变：你能逐行讲清、测试通过、lint 干净，才合入

## Q7：怎么衡量一次重构做得好不好？

**A**：用可观察的结果验收，而不是"感觉更优雅了"：
1. **行为不变**：重构前后同一套测试（含特征测试）全绿，关键输出一致
2. **坏味道减少**：目标坏味道（长函数/重复/深嵌套…）确实消除，可用静态指标辅助（圈复杂度、重复率、函数长度、依赖数）
3. **可测性提升**：新增/修改的代码更容易写单测，依赖可注入
4. **小步可回溯**：每个提交都是一个独立、可运行、可回退的绿状态
5. **没有夹带**：没偷偷改需求、没顺手改无关代码、refactor 与 fix/feat 分开提交
6. **别人更易读**：同事不看讲解能更快说清这段在做什么

满足这些，才是一次"安全且有价值"的重构。
